# 경기별 재추론 실행 경계와 운영 연결 과제

## 현재 경로

기존 `deploy/supervisor.py`는 배당·점수·선발 수집을 주기별 자식으로 실행하고 배당 저장 후 `src/live_market_refresh.py`가 기존 경기 문서를 갱신한다. 대용량 작업은 메모리 락을 공유하며 수집 성공과 판정 게시 실패를 구분한다. 서버는 준비된 응답과 마지막 정상값을 제공한다. 공식 사실 수집 `src/official_fact_capture.py`는 엄격한 경기 전 T-30 입력이고 `src/fact_delta_inputs.py`는 연구 입력을 검증한다. 기존 경기별 연구 어댑터 `experiments/accuracy-development-20261030/adapter.py`는 경기·팀·시장·시점과 고정 학습 상태를 검증해 `state.predict`를 호출하며 T-30 이후 거부한다. 라인업이 검증돼도 `player_effects_not_fitted`를 반환하고 선수 변경은 확률에 반영하지 않는다. 경기 중 교체·부상 효과를 처리하는 학습 모델은 확인하지 못했다.

## 구현과 안전 경계

`src/event_reinference.py`는 외부 요청·학습·저장·스케줄러를 직접 실행하지 않는 유한한 연구 배치 함수다. 호출자가 기준 시각, 경기별 완료된 입력 스냅샷, 가격·선수 정보 허용 경과 시간, 배치 수와 추론 횟수 한도, 독립 검증 함수와 추론 함수를 제공한다. 경기 예정·종료·연기·취소·라이브와 T-30을 구분하고, 경기/상품/시장/전체 배당 벡터와 관측·수신 시각을 확인한다. 중지·누락·오래된 가격, 시각 불명, 미래 수신, 오래된 선수 정보, 잘못된 경기, 검증 실패, 추론 오류 및 미지원 라이브는 결과 없이 보류한다. 배당 또는 라인업·부상·교체의 의미 내용이나 모델 버전이 바뀌면 해당 경기·상품만 추론하고, 수신 시각만 바뀐 동일 입력은 추론을 건너뛴다. 성공한 스냅샷보다 과거이거나 같은 관측 시각에 다른 가격/선수 상태를 제출하면 거부한다. 한도를 넘는 경기에는 deferred를 남기고 실패는 성공 이력을 갱신하지 않는다. 반환 상태에는 reason과 건수(요청·추론·동일·보류·할당량 대기)가 포함된다.

`polling_plan`은 수집 요청을 보내지 않고 경기 시각에 따라 6시간·1시간·15분의 **제안값**만 반환한다. 호출자가 원천의 제한·전체 요청 예산·시간 초과·재시도 정책을 보수적으로 적용해야 한다. 시작 30분 전부터의 제안은 없다. 이 값들은 운영 주기나 안전한 제공자 쿼터라는 뜻이 아니다. 연구 어댑터는 경기 중 추론을 지원하지 않으므로 이 경계는 라이브 재추론을 제안하지 않는다. T-30 동결 원장·기존 정산·모의 지갑을 전혀 수정하지 않는다.

검증자 `verify`는 전체 identity, 자료 수신 증거, 완전한 경기별 상태와 정확한 모델 스냅샷을 독립적으로 인증해야 한다. 호출자 선언이나 로컬 해시만으로 인증을 대신할 수 없다. `infer`도 기존 어댑터의 독립 계약 검사를 그대로 거쳐야 한다. 테스트는 합성 입력으로 기존 어댑터를 실제 호출했으며, 학습·운영 추론이나 성능 향상 검증이 아니다.

## 남은 통합 작업

이 구현은 운영 파이프라인에 연결되지 않은 실행 가능한 경계다. 신뢰할 수 있는 완전한 최신 스냅샷 공급자, 원천별 rate limit과 가격 중지 피드, 선수 ID·부상·교체 증거 검증 및 현재 상태 비교, 경기별 모델 상태 매핑이 필요하다. 신뢰 검증을 통과한 중지·실패 입력도 `last_seen`에 시각과 전체 입력 해시를 기록해 이전 열린 가격의 재생을 거부한다. 결과와 `last_success`, `last_seen`의 원자적 영속화·동시 실행 제어·재시작 복구는 호출자 책임이며, 검증이 실패한 원천의 최신 상태는 알 수 없으므로 보류해야 한다. 실패 중 이전 저장값을 현재 가격처럼 노출해서도 안 된다. 사실 종류의 삭제는 명시적 해소 사실로 표현해야 하며 종류가 사라지는 입력은 역순으로 보류한다. 목록 순서가 할당량 우선순위를 결정하므로 공정한 우선순위도 별도 설계해야 한다.

실제 선수 영향 모델, 라이브 점수·교체 반영 모델, 검증된 provenance와 독립 수신 증거가 확보되기 전에는 이를 적중률 개선이나 운영 추천 변경이라고 부르지 않는다. 사용자 인터페이스, 생산 DB, 운영 설정, 수집 주기, 배포는 변경하지 않았다.

## 기존 운영 경로와 연결 위치 재검토

운영의 실시간 배당 looper는 `src/odds_live.py --collect-only`로 수집 결과 `live_odds`를 먼저 저장한다. 그 자식이 끝난 다음 `deploy/supervisor.py`의 `_run_odds_cycle` → `_refresh_market_after_collection` → `_run_market_refresh`가 별도 `src/live_market_refresh.py` 자식을 실행한다. 후자는 `refresh_document`로 배당 변경을 평가하고 `record_live_market_revisions`로 T-30 이전 정확한 사전 판정을 원장에 기록·검증한 뒤 `picks_v2`를 저장한다. 실패 시 보류와 재시도가 있고, 정상 판정 후 준비된 웹 응답을 게시한다. `src/odds_live.py`를 독립 실행하면 자체적으로 `refresh_once`도 호출하므로 두 실행 모드를 중복 실행해서는 안 된다.

추가 연구 경계는 이 경로를 대체하지 않으며 기존 looper 외에 별도 scheduler·수집기·상시 프로세스를 만들지 않는다. 향후 검증된 사실이 들어오면 기존 수집 완료와 사전 원장 판정의 성공 여부를 확인한 후 해당 경기·상품의 불변 입력을 기존 작업 흐름에서만 구성하고, 한 번에 제한된 작업을 별도 자식에서 처리하는 연결을 검토한다. 사전 픽 동결이나 원장 결과를 바꾸지 않는 독립 연구 산출물로만 보관하며, 성공 결과·`last_success`·`last_seen`을 하나의 트랜잭션으로 기록하고 장애 시 보류해야 한다. 지금은 신뢰 검증자, 실제 입력 매핑, 원자적 저장 및 호출 지점이 없어 **운영 경로에 실제 연결되지 않았다**. 연구 상태를 핸들러나 `_run_market_refresh` 안에서 직접 실행하거나 전체 `picks_v2` 반복 로드로 구현하지 않는다.

기존 서버는 1GB 머신에서 배당 수집 자식과 판정 자식을 순차 실행하고 `_memory_heavy_lock`과 `_score_refresh_lock`으로 무거운 보조 작업과 점수 갱신을 조정한다. 512MiB 여유 기준은 진입 검사이지 OOM 방지 보증이 아니다. 새 연결은 기존 락/슬롯과 작업 우선순위 안에서 직렬화하고, 사전에 별도 로컬 fixture의 피크와 전체 작업 예산을 측정해야 한다. 기존 수집 주기·메모리 기준이나 retry 계약은 여기서 변경하지 않는다.

## 이미 존재하는 경기 중 LIVE 상황 추정

`web/src/lib/saved-live-prediction.js`는 동결된 사전 예측·확률과 최근 점수 피드를 확인한 후 `web/src/lib/bet-ledger.js`의 `estimateLiveProbability`를 사용한다. 이는 사전확률에 현재 점수와 진행도를 결합하는 **검증 모델이 아닌 휴리스틱 추정치**이며, 별도 경기 중 선수 영향 모델이 아니다. 축구는 경과 분/90, 야구는 이닝 텍스트를 쓰고 농구·배구는 실제 시계 모델 없이 `STARTED`일 때 기본 진행도 0.5다. 시장 화면은 저장된 선택과 원본 확률을 보존하고 10분보다 오래된 피드, 점수 누락, 지원하지 않는 시장을 보류한다. 교체·부상 필드는 이 계산에 사용되지 않는다. 합성 JS 테스트에서 점수와 시간 변경은 추정치를 바꾸지만 교체·부상 필드만 바꾸면 결과가 같았고, 농구·배구 기본 진행도 및 오래된 피드 보류를 확인했다. 이는 실제 원천이나 예측 성능을 검증한 결과가 아니다.

연구 배치의 `live_research_adapter_unsupported`는 위의 기존 화면 추정치가 없다는 뜻이 아니다. 현재 연구 어댑터는 경기 중 입력을 받지 못하고 교체·부상 효과도 학습하지 않았다는 의미다. 원장 게시의 보수적 경계에 맞춰 배치에서도 T-30 정각부터 새 사전 추론을 보류한다. 연구 어댑터 자체는 정각을 허용하지만 운영 원장의 `>= T-30` 거부보다 넓게 사용하지 않는다.
