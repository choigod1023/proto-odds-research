# 경기별 재추론 실행 경계와 운영 연결 과제

## 현재 경로

기존 `deploy/supervisor.py`는 배당·점수·선발 수집을 주기별 자식으로 실행하고 배당 저장 후 `src/live_market_refresh.py`가 기존 경기 문서를 갱신한다. 대용량 작업은 메모리 락을 공유하며 수집 성공과 판정 게시 실패를 구분한다. 서버는 준비된 응답과 마지막 정상값을 제공한다. 공식 사실 수집 `src/official_fact_capture.py`는 엄격한 경기 전 T-30 입력이고 `src/fact_delta_inputs.py`는 연구 입력을 검증한다. 기존 경기별 연구 어댑터 `experiments/accuracy-development-20261030/adapter.py`는 경기·팀·시장·시점과 고정 학습 상태를 검증해 `state.predict`를 호출하며 T-30 이후 거부한다. 라인업이 검증돼도 `player_effects_not_fitted`를 반환하고 선수 변경은 확률에 반영하지 않는다. 경기 중 교체·부상 효과를 처리하는 학습 모델은 확인하지 못했다.

## 구현과 안전 경계

`src/event_reinference.py`는 외부 요청·학습·저장·스케줄러를 직접 실행하지 않는 유한한 연구 배치 함수다. 호출자가 기준 시각, 경기별 완료된 입력 스냅샷, 가격·선수 정보 허용 경과 시간, 배치 수와 추론 횟수 한도, 독립 검증 함수와 추론 함수를 제공한다. 경기 예정·종료·연기·취소·라이브와 T-30을 구분하고, 경기/상품/시장/전체 배당 벡터와 관측·수신 시각을 확인한다. 중지·누락·오래된 가격, 시각 불명, 미래 수신, 오래된 선수 정보, 잘못된 경기, 검증 실패, 추론 오류 및 미지원 라이브는 결과 없이 보류한다. 배당 또는 라인업·부상·교체의 의미 내용이나 모델 버전이 바뀌면 해당 경기·상품만 추론하고, 수신 시각만 바뀐 동일 입력은 추론을 건너뛴다. 성공한 스냅샷보다 과거이거나 같은 관측 시각에 다른 가격/선수 상태를 제출하면 거부한다. 한도를 넘는 경기에는 deferred를 남기고 실패는 성공 이력을 갱신하지 않는다. 반환 상태에는 reason과 건수(요청·추론·동일·보류·할당량 대기)가 포함된다.

`polling_plan`은 수집 요청을 보내지 않고 경기 시각에 따라 6시간·1시간·15분의 **제안값**만 반환한다. 호출자가 원천의 제한·전체 요청 예산·시간 초과·재시도 정책을 보수적으로 적용해야 한다. 시작 30분 전부터의 제안은 없다. 이 값들은 운영 주기나 안전한 제공자 쿼터라는 뜻이 아니다. 경기 중 모델이 없으므로 라이브 재추론도 제안하지 않는다. T-30 동결 원장·기존 정산·모의 지갑을 전혀 수정하지 않는다.

검증자 `verify`는 전체 identity, 자료 수신 증거, 완전한 경기별 상태와 정확한 모델 스냅샷을 독립적으로 인증해야 한다. 호출자 선언이나 로컬 해시만으로 인증을 대신할 수 없다. `infer`도 기존 어댑터의 독립 계약 검사를 그대로 거쳐야 한다. 테스트는 합성 입력으로 기존 어댑터를 실제 호출했으며, 학습·운영 추론이나 성능 향상 검증이 아니다.

## 남은 통합 작업

이 구현은 운영 파이프라인에 연결되지 않은 실행 가능한 경계다. 신뢰할 수 있는 완전한 최신 스냅샷 공급자, 원천별 rate limit과 가격 중지 피드, 선수 ID·부상·교체 증거 검증 및 현재 상태 비교, 경기별 모델 상태 매핑이 필요하다. 신뢰 검증을 통과한 중지·실패 입력도 `last_seen`에 시각과 전체 입력 해시를 기록해 이전 열린 가격의 재생을 거부한다. 결과와 `last_success`, `last_seen`의 원자적 영속화·동시 실행 제어·재시작 복구는 호출자 책임이며, 검증이 실패한 원천의 최신 상태는 알 수 없으므로 보류해야 한다. 실패 중 이전 저장값을 현재 가격처럼 노출해서도 안 된다. 사실 종류의 삭제는 명시적 해소 사실로 표현해야 하며 종류가 사라지는 입력은 역순으로 보류한다. 목록 순서가 할당량 우선순위를 결정하므로 공정한 우선순위도 별도 설계해야 한다.

실제 선수 영향 모델, 라이브 점수·교체 반영 모델, 검증된 provenance와 독립 수신 증거가 확보되기 전에는 이를 적중률 개선이나 운영 추천 변경이라고 부르지 않는다. 사용자 인터페이스, 생산 DB, 운영 설정, 수집 주기, 배포는 변경하지 않았다.
