# 2026-10-30 응답 재전송 조사

## 경로와 재현

첫 점검에서 기록한 `/api/picks` 39,682,129 bytes·8.893초는 압축을 요청하지 않은 단일 운영 측정이다. 이번에는 운영을 반복 호출하지 않았다. 대시보드와 프로토 배당표는 각각 이 전체 API를 첫 진입, 60초 간격, focus/online/visible 때 요청한다. 목록 화면은 `/api/matches?scope=recent`를 쓰며 해당 경로가 404인 구형 서버에서만 `/api/picks`로 대체한다. 상세는 list revision을 붙인 `/api/match-detail`이다. 목록의 최근/전체/성과 view는 별도 캐시를 사용하며 이번 수정 대상이 아니다.

콜렉터는 DB에 저장된 picks JSON을 gzip으로 준비해 캐시하고, gzip 미지원 요청에는 매번 압축을 푼다. 이전 UI polling은 `no-store`, 매 요청 timestamp와 `no-cache`를 사용하며 항상 전체 본문을 읽어 이전 문자열과 비교했다. 동일하면 JSON.parse는 이미 생략했지만 다운로드·문자열 생성과 비교는 반복됐다. ETag 또는 If-None-Match는 이 경로에 없었다. 구조적으로 DB의 JSON을 요청마다 재직렬화하지는 않으며, 상태가 같아도 전체 본문을 반환하는 문제가 확인됐다.

## 변경과 제한

서버가 실제 선택해 반환할 picks 본문의 SHA-256으로 약한 ETag를 만들고, 동일 태그의 조건부 요청에는 304와 빈 본문을 반환한다. gzip/identity는 같은 JSON의 표현이므로 약한 태그를 공유하고 Vary를 유지한다. 캐시 재구축 대기·실패 시에도 실제 제공할 마지막 정상 본문의 태그를 비교한다. 브라우저는 ETag가 있을 때만 다음 폴링에 조건을 붙이고 304는 기존 데이터로 유지한다. 첫 요청·새 본문·기존 서버·오류 복구 및 60초/복귀 재조회는 유지한다. CORS는 If-None-Match를 허용하고 ETag를 노출한다. 리스트 revision/detail 계약과 필드는 바꾸지 않는다.

`python experiments/terra-serving-payload-20261030/measure.py`는 저장소 fixture SHA256 `abe9350eee06ccf8a510c0295d4af8364e5d168f9174ee94d2c286c697822efa`를 사용한다. 로컬 UTF-8 본문 12,348,659 bytes, gzip 1,356,840 bytes. 같은 gzip 본문을 두 번 요청하면 기존 본문 합계 2,713,680 bytes, 변경 후 1,356,840 bytes (두 번째 0; HTTP 헤더 제외). 양쪽 본문 JSON은 동일하다. 동일 두 번째 응답의 브라우저 text 읽기는 1→0회이고 JSON.parse는 기존에도 0회였다. 서버 원본 읽기 1회. 이는 로컬 fixture의 바이트 비교이며 실 운영 대역폭·시간 개선이나 평균 지연을 뜻하지 않는다.

실제 로컬 HTTP 테스트에서 OPTIONS, gzip 첫 200, 태그 및 CORS 노출, 조건부 304, 변경 후 새 200을 검증했다. JS 테스트는 첫 로딩·동일·변경·구형 서버·실패 복구를 확인한다. 전체 Python 및 프론트 테스트와 격리 빌드 결과는 handoff에 기록한다. 실제 브라우저 시각 검증 및 배포 후 확인은 수행하지 않았다. 304가 프록시에서 변형되는지, 운영의 트래픽 분포, 첫 대형 응답의 전송·생성 지연은 별도 검증이 필요하다.
