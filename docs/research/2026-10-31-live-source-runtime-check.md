# 운영 배당·판정 응답 읽기 전용 확인

2026-10-31 13:38~13:40 KST에 공개 응답과 Fly 상태·최근 로그를 읽었다. 수집기나 판정 프로세스는 수동 실행하지 않았다. 최초 로컬 스냅샷 조사는 파일만 검사한 결과이며, 아래 운영 확인과 구분한다.

- 저장소 `deploy/supervisor.py`는 `odds_live.py --collect-only`를 60초 간격으로 계획하고, 별도 자식에서 `live_market_refresh.py`를 실행하는 경로를 포함한다. 이는 코드 설정이며 배포 커밋·실행 주기의 실측 증명은 아니다.
- 읽기 전용 Fly 상태에서 머신 1대가 `started`였다. 최근 로그 100줄(04:21:11~04:39:31 UTC)의 제한된 키워드 분류에서 배당 관련 줄 15개가 있었고 시작 12개·성공 2개로 분류됐다. 로그 보존 범위·문자열 분류 한계 때문에 모든 작업의 성공률이나 판정 실행 여부를 확정하지 않는다.
- 공개 [배당 API](https://proto-odds-collector.fly.dev/api/live-odds)는 HTTP 200, 947개 행, 회차 128~131을 반환했다. 수신 04:38:26 UTC에서 `generated_at`은 04:37:59 UTC로 약 27초 전이었다. 04:39:25와 04:40:03 UTC에도 같은 생성시각이었으며 마지막 관측 당시 약 125초 전이었다. 약 98초의 제한된 관측 동안 갱신이 확인되지 않았다는 뜻이며 장기 중단이나 갱신 주기를 확정하지 않는다. API 응답은 각각 약 0.6~1.6초였고 이는 네트워크 왕복·본문 수신 시간이지 원천 가격 지연이 아니다.
- 배당 원천의 실제 가격 변동 시각이나 원천 HTTP 수신시각은 이 응답으로 입증하지 못했다. 기존 `odds_live.py`의 빈 응답 경로는 직전 가격을 유지하면서 생성시각을 새로 기록할 수 있으므로 생성시각만으로 원천이 최신이라고 단정하면 안 된다. 관측 시점에 그 fallback이 실제 발동했는지는 미확인이다.
- [헬스 응답](https://proto-odds-collector.fly.dev/health)은 HTTP 200/`ok`였으나 04:39:53 UTC의 `picks_generated_at`은 전날 10:13:55 UTC(약 18시간 26분 전), `picks_stored_at`은 전날 10:17:23 UTC였다. [판정 API](https://proto-odds-collector.fly.dev/api/picks)의 04:38:46 UTC 응답은 `generated_at` 전날 09:18:08 UTC로 약 19시간 21분 전이었다. 두 생성시각은 약 55분 47초 다르다. 메타데이터와 공개 본문의 불일치는 실측이지만 원인이나 배포 버전은 확인하지 못했다. `artifact_responses.py`는 메모리 슬롯이 없거나 재구성 실패 시 이전 본문을 반환할 수 있으나, 이 가능성이 실제 원인인지 증거가 없다.
- 04:39 UTC 배당의 `경기전` 상품 520개 중 판정 응답 `live`의 회차·게임번호가 같은 상품은 453개, 없는 상품은 67개였다. 이 비교는 상품번호 존재만 검사하며 정식 경기·동일 상품 검증이나 누락 원인, 개별 추천 오류를 입증하지 않는다.
- 감시 이슈 [#447](https://github.com/choigod1023/proto-odds-research/issues/447)은 열린 상태였다. 2026-10-30 23:50 UTC 마지막 감시 기록은 판정 DB 생성시각 816분 지연(경보 90분)을 기록했다. GitHub Actions 작업의 success는 감시 작업 실행 성공이지 데이터 정상 판정이 아니다.

판정 값이 오래된 원인은 아직 모른다. 변경이 없어 `refresh_once`가 저장하지 않는 정상 경로, 수집·판정 작업 실패 또는 지연, 응답 캐시와 DB 간 차이 등은 구분이 필요하다. 기존 열린 사고 및 승인된 운영 절차에 따라 총괄이 실제 배포 리비전·수집/판정 로그·DB 메타데이터·제한된 경기별 대응을 점검해야 한다. 이 관측은 배포·재시작·데이터 변경을 포함하지 않는다.
