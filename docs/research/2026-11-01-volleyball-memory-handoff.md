# 2026-11-01 배당 판정 메모리·락 경합 조사

## 운영 관측

2026-11-01 04:46~05:03 KST(10월 31일 19:46~20:03 UTC) `fly logs --no-tail`을 UTF-8로 읽었다. 19:53:18 UTC 실시간 배당 652건을 저장했으나 후속 시장 판정은 19:46:52·19:48:52·19:53:40·19:56:40·20:03:01 UTC에 여유 469·472·467·473·465MiB / 필요 512MiB로 각각 시작 전 보류됐다. 이 구간은 배당 수집 성공과 판정 실패가 별개임을 보여준다. 전체 정체 기간에 같은 원인만 있었거나 OOM이 없었다고 입증하지 않는다.

별도 경합도 있었다. 19:54:40 UTC 저장된 배당 재판정이 공유 메모리 락을 얻지 못해 즉시 rc=1로 끝났고, 19:55:27 UTC 웹 응답 준비가 build 65.97초로 끝났다. 로그의 완료 시각과 경과 시간으로 역산한 시작은 약 19:54:21 UTC이므로 락 경합 시점과 겹친다. 당시 코드에서 웹 응답 준비와 판정은 같은 `_memory_heavy_lock`을 쓴다. 다만 로그만으로 락 소유자의 정확한 thread identity는 확인하지 못했으며, 해당 응답 준비와의 경합이 유력한 정황이다.

20:03:54 UTC 프로세스 스냅샷에서 supervisor로 관측된 PID 605 python RSS 278,284KiB, HWM 377,900KiB, 다른 python 두 개 RSS 64,564·95,176KiB, MemAvailable 355,064KiB였다. 동시 프로세스와 시점이 다른 값이므로 이를 더해 판정 피크로 부르지 않는다. 저장된 응답 스냅샷 파일은 15,238,610 bytes였고 gzip 목록·압축 상세를 포함한다. RSS 전부를 그 파일이나 특정 캐시가 차지한다고 추정할 수 없다. 서버 코드·DB·스케줄·프로세스를 변경하거나 별도 부하를 실행하지 않았다.

## 수정 범위와 한계

`_refresh_market_after_collection`이 이미 다른 작업이 보유한 공유 락을 만났을 때 즉시 실패하지 않고 **최대 60초** 기다린다. 기존 작업을 중단하지 않으며 락을 얻은 뒤에도 기존 256MiB 사전 검사와 512MiB 판정 직전 검사, 점수 락, 실패 시 retry, 동결 원장, 마지막 정상 응답을 그대로 유지한다. 락 대기 중 `_market_cycle_pending`과 배당/추천 락을 유지하므로 저장된 배당 판정에 대한 우선권이 유지된다. 60초가 지나면 기존처럼 실패·재시도한다. 이 대기는 각 시도에 최대 60초의 추가 지연을 줄 수 있고 그 뒤 기존 점수 락·판정 시간도 별도로 걸린다. retry 횟수·기한 검사는 기존처럼 시도 사이에 한다.

이 변경은 위에서 확인한 **락이 곧 해제되는 경우의 불필요한 조기 실패**만 다룬다. 512MiB 미만이 계속되면 여전히 보류되며, 이것만으로 배구 경기 표시나 장시간 picks 정체가 해결된다고 주장할 수 없다. 메모리 기준을 낮추거나 캐시·DB를 삭제하지 않았다. 원인별 메모리 구성을 아직 알 수 없고, 새 코드의 실제 1GB 피크 및 성공률도 측정하지 않았다.

## 재현과 #478

로컬 thread 회귀 테스트는 기존 작업이 락을 잡은 상태에서 실제 saved-price retry를 시작하고, 대기 중 우선 예약과 작업 비중단을 확인한 후 락 해제 시 재수집 없이 판정이 1회 실행되는지 검사한다. 별도로 대기 시간 초과와 여유 470MiB에서 판정 미실행, 락 해제를 검사한다. 해당 범위 포함 Python 61개, 전체 Python 2,152개 통과(6개 건너뜀, subtest 93개). 독립 작업 공간에서 [#478](https://github.com/choigod1023/proto-odds-research/pull/478)의 head `d184f27814e0801e3c8cba4d9cf4d8322bbee010`와 이 패치를 모두 적용한 후 대기·재시도·픽스터 관련 테스트 51개를 통과했다. 이는 합성 상호작용 검사이며 두 PR의 순서나 운영 성공을 보장하지 않는다.

기존 `scripts/measure_match_response_memory.py`를 로컬 Windows 저장소 fixture로만 실행했다. 632경기에서 예전 in-process 경로 parent RSS 67,020KiB/peak 88,556KiB, 기존 isolated 경로 parent RSS 31,180KiB/peak 49,576KiB였다. fixture·플랫폼·동시 부하가 운영 2,969경기와 달라 운영 개선 수치나 안전 한도로 쓰지 않는다.

이후에는 동등 크기의 격리 입력에서 parent·워머·판정 자식의 피크와 겹침을 따로 계측하고, 메모리 512MiB 미달이 계속되는 구조를 해결할 근거가 필요하다. 실제 코드 병합과 배포, 재시작은 별도 상태다.

## 2026-11-01 추가 메모리 원인 조사

05:04~06:06 KST(10월 31일 20:04~21:06 UTC)에 동일 수집기를 읽기 전용으로 재확인했다. 20:56:57 UTC 판정 직전 여유 464MiB였고 기준 512MiB보다 48MiB 부족했다. 21:02:18 UTC에는 공유 락 경합으로 저장 배당 판정이 보류됐으며 21:02:28 UTC 웹 응답 준비가 완료됐다. 이 관측은 기존 락 수정이 여전히 부분적일 뿐임을 뒷받침한다. 장기간 전체의 근본 원인이나 OOM 여부를 증명하지 않는다.

격리 Windows 실험 `python experiments/volleyball-memory-gate-20261101/profile_fixture.py`는 저장소 632경기를 복제해 2,969개의 합성 ID를 만든 41,573,425-byte fixture(SHA256 `ed788b0f1f7f00bf29bfc3e0cb5d1cf1ade729875c3470d7d51fdf47ed530b2b`)를 사용한다. 별도 임시 SQLite에서 3개 revision을 준비한 뒤 부모 프로세스 RSS/HWM을 비교했다. 구 in-process 구현은 174,816/281,428KiB, **이미 운영 코드에 있는** isolated 구현은 45,316/126,684KiB였고 각 상세 2,969개와 목록 gzip 크기 192,424 bytes가 같았다. 이는 운영 전후 실험이나 이번 PR의 신규 절감량이 아니다. Windows와 합성 자료이며 자식 피크·동시 운영 부하·운영 JSON 필드 분포와 allocator를 재현하지 못한다. 기존 상세/목록 회귀 테스트는 내용 일치를 별도로 검사한다.

따라서 512MiB를 유지하면서 운영에서 판정을 다시 시작할 만큼 추가로 메모리를 회수하는 안전한 패치는 아직 입증하지 못했다. 런타임 전체를 무작정 비우거나 메모리 기준을 낮추지 않았다. 다음 단계는 격리 Linux에서 운영과 동등한 크기·필드 분포의 비식별 fixture로 부모의 살아 있는 객체/allocator 구성과 동시 요청·워머의 부모 및 자식 피크를 분리 계측하고, 마지막 정상 응답과 정확한 detail revision을 보존하는 후보만 전후 비교하는 것이다. 운영 자료를 복사하거나 서버 재시작/DB 변경은 하지 않았다.
