# 누락 경기 판정 복구와 응답 메모리

## 확인한 현상

11월 1일 공개 배당에는 야구·농구·배구가 있으나 picks_v2 생성 시각은
10월 30일 10:13:55 UTC에 머물렀다. 표시 전용 누락 목록은 실제 판정 복구가 아니다.
운영 로그에서 판정 시작은 점수 수집 종료 후에도 가용 442~465MiB가
고정 512MiB 조건보다 작아 보류됐다. supervisor는 이미 뷰 작업 세트 해제,
GC, malloc_trim과 자식 프로세스 응답 준비를 사용한다.

부모 프로세스 익명 메모리의 구체적 보유 객체는 읽기 전용 /proc만으로
특정하지 못했다. 다만 artifact HTTP 응답 생성은 여전히 전체 JSON TEXT,
UTF-8 바이트, 압축 바이트를 함께 할당하는 코드 경로였다.

## 변경

- picks_v2를 SQLite 읽기 스냅샷의 blob에서 해석하고 문서 내부 키를 공유한다.
  큰 정수·긴 지수·escaped surrogate의 기존 JSON 의미를 회귀 검증한다.
- 원장 전체 행과 해시 체인 검증은 유지하면서 행 사이의 불변 문자열만
  제한된 풀로 공유한다. 배열·객체와 저장된 원장은 공유/변경하지 않는다.
- 큰 JSON 문자열을 한 번에 만들지 않고 SQLite TEXT에 조각으로 기록한다.
  두 번째 직렬화 실패/길이 변경은 본문과 revision 모두 롤백한다.
- HTTP artifact 응답을 64KiB 조각으로 바로 gzip 처리한다. 기존 원문 SHA-256
  ETag, 같은 DB 스냅샷의 revision, 실패 시 마지막 정상 응답을 유지한다.
- 저장 배당의 판정이 대기하고 이미 응답이 있으면 주기적 워머가 슬롯을 양보한다.
  첫 응답 준비와 판정 직후 게시 경로는 유지한다. 512MiB 시작 조건은 낮추지 않았다.

## 실제 실행한 검증

`tests/test_current_fixture_recovery.py`는 통제된 경기 전 시각의 새 야구·농구·배구를
실제 refresh_once, 임시 SQLite, 해시 원장, MatchViews로 통과시킨다.
각 종목 판정 기록과 언더/오버 옵션 생성, 기존 동결 경기 불변, 중복 실행의
원장 멱등성을 검증한다. 이는 운영 경기 전 기록을 소급 생성한 결과가 아니다.

`scripts/measure_market_refresh_memory.py`는 외부 DB 인자를 거부하고 네트워크를
차단한 자식에서 저장소 fixture로 만든 2,969경기, 예측 7,780개, 정산 1,241개를
비교한다. 원장 예측 JSON은 97,695,795문자(운영 관측 60,491,308문자보다 큼)다.
역사 결과는 합성 1,000행이며 배당 피드는 비어 있다. 새 경기 생성과 전력 이력
조회는 별도 소형 회귀 테스트가 담당하므로 운영 최대 메모리로 일반화하지 않는다.

Windows 최종 비교:

- 판정 peak: 639,968KiB → 473,388KiB 수준. 약 26% 감소.
- 처리 시간: 약 4초 → 11초. 메모리를 줄이는 대신 직렬화 시간이 늘었다.
- HTTP 응답 생성 peak: 217,704KiB → 39,072KiB. 원문 ETag와 압축 크기 동일.
- 판정 artifact와 원장 해시, 정산 1,241개가 동일했다.

초기 순수 Python 스트리밍 읽기만 적용한 후보는 오히려 메모리와 시간이 늘어
그대로 채택하지 않았다. 작은 원장만 썼을 때의 개선을 최종 측정으로 삼지 않았다.
Linux Python 3.11(운영 이미지)과 3.12의 CI에서도 같은 스크립트를 실행한다.
간헐적인 /proc 관측이나 합성 테스트로 무장애·운영 최대 RSS를 입증하지 않는다.

## 언더/오버가 대표 픽에 없는 이유

언더/오버 가격과 옵션은 수집·생성된다. 현재 대표 선택 정책은 경기 전체
승패/승무패의 픽스터 투표이며, 합계 시장의 투표·기준점 모델은 이 정책에
포함되지 않는다. 정책을 실행하면 일반 옵션 점수만으로 언더/오버를 대신
대표 픽으로 고르지 않는다. 이는 수집 누락과 별개다. 이번 수정은 언더/오버
확률·ROI 우세를 주장하거나 대표 선택 정책을 확대하지 않는다.

## 운영 확인의 경계

코드 병합과 실행 중인 Fly 이미지 반영은 다르다. 이 변경은 새 이미지가 필요하다.
배포 전에는 운영 누락이 해결됐다고 보고하지 않는다. 배포 후 새 자동 수집에서
비축구 경기, 실제 판정 revision, 목록/상세 생성 시각, 메모리와 실패 로그를
확인해야 한다. 이미 T-30이 지난 경기에 사전 예측을 새로 만든 척하지 않는다.
