# 메모리 대기에 막힌 후보 원천 수집 보완

PR #416을 CI 통과 후 `66f1c255b41714dabc6dc0638bbd8f1e12e13006`으로 병합하고 운영에 반영했다. 운영 Python 3.11.18에서 두 동결 후보 모듈의 로드를 확인했다. 2026-10-29 14:32:51 UTC에 health HTTP 200/0.375초, 최근 목록 HTTP 200/0.334초를 관측했다. 이는 단일 구간의 응답 확인이며 장기 안정성·무장애 증거가 아니다.

14:33:14 UTC 읽기 전용 DB 확인에서 `player_info`의 마지막 저장은 **10:38:48 UTC**, 새 후보 상태 문서는 아직 없었다. 기존 전체 선수 수집 작업이 512MB 입장 조건에 막히면 원천 수집까지 수 시간 지연될 수 있어, 코드 배포만으로 자동 수집이 정상화됐다고 판단할 수 없었다.

## 보완한 경로

- 별도 프로세스/서버를 만들지 않고 기존 5분 KBO 선발 작업에서 작은 후보 원천 확인을 이어 실행한다. 정상 KBO 자료를 먼저 저장하고, KBO 원천 실패 때도 후보 확인은 독립적으로 시도한다. 후보 확인 실패는 정상 KBO 수집을 실패로 바꾸지 않는다.
- MLB 경기 ID·시작·홈/원정 **네 필드만 SQL에서 투영**한다. 전체 다종목 선수 JSON·과거 통계·부상 목록을 Python으로 읽지 않는다. 캐시 일정은 요청 대상을 찾는 용도이며 경기 전 상태를 증명하지 않는다. 실제 feed의 경기 ID·시각·S/P 상태·투구 없음·완전한 9인 타순 검증을 그대로 거친다.
- 원천은 회당 MLB 최대 1경기(5분 단위 순환), KBO 일정 최대 2일이다. 연결/읽기 timeout은 2/3초, 각 원천의 전체 예산은 6초이며 진행 중 네트워크 요청이 끝나는 시간은 추가될 수 있다. 본문 크기 제한은 유지한다. 4분 재호출 방지와 KBO 일정의 별도 25분 예산을 둔다.
- 전체 선수 작업의 오래된 `updated_at`을 새것으로 바꾸지 않는다. 새 MLB 공식 feed는 별도 작은 문서에 실제 수신 완료 시각으로 저장한다. 경량 판정은 정확한 경기의 두 원천 중 가용 시각이 더 최근인 적격 후보 입력을 사용한다.
- 전체 모델 학습이나 야구 경기 예측은 이 원천 작업에서 실행하지 않는다. KBO의 작은 고정 seed·증분 상태 생성은 필요할 때만 수행하고, 예측과 공식 연구 정산은 기존 판정 경로를 사용한다. 실제 추천·T-30·월 손실 5만 원 지갑 제한은 바꾸지 않는다.

기존 KBO 작업은 `_score_refresh_lock`으로 판정 게시와 겹치지 않게 실행된다. 소량 원천 요청이 더해져 해당 잠금을 잡는 시간이 늘 수 있다. 따라서 네트워크 예산을 전체 선수 작업보다 작게 고정했다. 모든 MLB 경기 확보나 원천의 타순 발표 시각을 보장하지는 않으며 누락/실패/현재 후보 수는 `baseball_candidate_watch` 문서에 기록한다.

## 검증

전체 로컬 Python: **1,845 passed, 6 skipped, 93 subtests passed**. 새 회귀는 1MB 불필요 내용이 있는 선수 문서의 scalar 투영, 전체 문서 역직렬화 금지, 실제 SQLite→작은 원천 문서→경량 판정 입력 전달, 5분 순환/예산, cooldown, KBO 실패와 후보 실패의 독립성을 확인했다. 실제 HTTP가 없는 합성 원천 회귀를 전향 운영 관측으로 부르지 않는다.

새 경로의 실제 운영 실행 여부는 배포 후 `baseball_candidate_watch.checked_at`, KBO 상태와 MLB 대상/수집 사유를 읽어 확인한다. 타순 미발표나 대상 경기 없음은 숫자 예측 성공으로 표시하지 않는다. 후속 운영 증거는 이 디렉터리의 배포 검증 파일로 별도 보존한다.
