**실제 연결 차단: 여러 경기 입력의 행별 검사 범위.** #467의 `run_capture_pipeline`은 각 ready row를 확인할 때 `all(eligible_fact(f,row,bundle) for f in facts)`로 전체 경기의 사실을 그 한 row와 대조한다. 격리된 합성 두 경기에서 실제 어댑터로 생성한 두 row는 각각 ready였고, 각 row와 자기 경기 사실의 `eligible_fact`도 각각 true였다. 그런데 두 row를 한 bundle로 전달하면 각 row가 상대 경기 사실과도 맞아야 하므로 `unsupported_ready_input`으로 전체가 거부됐다. raw bundle만 저장되고 manifest는 생성되지 않았다. 경기별 공식·canonical ID와 상품 ID로 사실을 먼저 분할하고 각 row에 대응하는 사실 집합만 검증하며, 미연결·혼합·중복은 실패시키는 방식의 수정과 회귀 검사가 필요하다. 이는 합성 자료의 재현이며 현 수집 표본에 확정 사실이 두 경기 존재했다는 뜻이 아니다.

CLI는 계획만 만들며 실제 메시지를 보내지 않았다.

## 후속 실코드 검토: 확인된 차단 사항

2026-10-31 후속 배정에서 총괄의 미커밋 queue를 읽기 전용으로 두 번 복제해 실행했다. 두 번째 스냅샷 원본 SHA256은 `319ba7c6fae5a9acff2da63dbc1459882008070d66625706c7540aa42337177a`이고, 검토 사본에서는 실제 채팅 ID 10개만 비활성 테스트 문자열로 치환했다. 원본 해시와 치환 사본 해시는 `vendor/queue_v2/source-hashes.json`에 있다. 코드가 작성 중 변했으므로 아래는 지정 SHA의 동작이며 총괄 최종본 판정이 아니다.

1. **초기 seed 부재:** 빈 queue에서 이미 알고 있는 입력을 `publish`하면 곧바로 pending을 만든다. 현재 노출된 API/CLI에는 기존 known 입력을 작업 없이 seen에 등록하는 seed 명령이 없다. 따라서 별도 seed 절차 없이 기존 자료를 첫 publish하면 ‘새 자료가 생길 때만’ 조건을 만족하지 못한다. 기존 445개 회고 자료가 실제로 ready 사실로 변환됐다는 뜻은 아니다. 초기화 시 known semantic signature만 원자적으로 저장하고 작업을 만들지 않는 명시적 경로가 필요하다.
2. **검증 후 manifest의 신뢰 플래그·임의 필드 변조:** 유효 manifest의 `cases[].input.source_evidence[].external_receipt_verified`를 false에서 true로 바꾸고 `prompt`·`threadId`를 추가해도 `validate_manifest`가 통과했으며 변경된 내용이 content-addressed input 파일에 보존됐다. semantic hash는 바뀌지 않아 원본 재전달도 중복으로 처리됐다. 이는 queue가 raw source를 인증해야 한다는 뜻이 아니다. adapter 출력 이후 위변조를 검출하고 source verification 상태를 무결성/의미 해시에 묶어야 한다는 뜻이다. 고정 prompt 생성은 이 임의 문자열을 직접 명령으로 사용하지 않았고 실제 메시지는 보내지 않았다. 변조 방지 또는 미신뢰 데이터 경계가 없으면 후속 소비자가 가짜 인증·지시를 신뢰할 위험이 있다.
3. **요청 생성 helper가 저장된 claim을 재확인하지 않음:** pending 작업의 안전한 input path/hash를 그대로 두고 호출 인자만 `state=claimed`, 다른 64자 event_id로 바꾸자 `dispatch_request`가 고정 worker 대상 요청을 생성했다. 요청 생성만 검증했고 전송은 하지 않았다. CLI `prepare`는 저장된 작업을 먼저 읽으므로 동일 반례를 CLI 임의 event ID로 바로 재현한 것은 아니다. 다만 helper의 다른 호출자 또는 CLI가 status를 읽은 뒤 상태가 변하는 경쟁 상황에서는 stale claim을 재확인하지 않는다. 저장된 job ID·input SHA·league·claimed 상태와 event의 일치 확인을 잠금 안에서 수행하고, 실제 전송 결과 불확실성은 별도 보존해야 한다.
4. **수집기와 미완성 어댑터의 인증 경계 불일치:** #467 head `13607afe4177be6ab16bf6c0b7be800c7a1bdabd`의 `eligible_fact`는 공식 근거의 `external_receipt_verified=True`라는 호출자 값을 요구한다. 당시 개발 중 어댑터 스냅샷 SHA256 `78dce09f8af94a79934834c63c3f9935a3fb209826fe822b64a012996c23ce33`은 외부 인증을 구현하지 않고 결과 근거를 항상 false로 표기한다. 합성 변환기에서 임의로 true를 주장한 원문 사실을 넣으면 수집기·실제 어댑터·실제 queue 연결이 ready로 통과했지만 어댑터 출력 근거는 false였다. 외부 증인을 구현하거나 true를 독립 검증한 것은 아니다. 반대로 원문의 false는 수집기에서 ready를 막는다. 조건과 출처의 계약을 통일하고, self-asserted true를 인증 증거로 해석하지 않도록 해야 한다. 어댑터 최종 PR/head는 조회 시 확인되지 않았고 이 결과를 그 최종 코드에 귀속하지 않는다.

동일 입력 반복과 receipt 시각만 변경한 경우 중복 작업이 생기지 않았고, 다른 리그로 작업을 분리했다. uncertain은 자동 claim되지 않았으며 operator 확인 없는 pending 복귀를 거부했다. input_path traversal과 저장 입력 바이트 변조도 거부했다. CLI는 publish/claim만 수행하고 메시지를 보내지 않았다. `claim`은 한 호출당 최대 3개지만 두 번 호출해 총 4개 리그가 동시에 claimed 상태가 될 수 있었다. 3개가 전역 동시 상한인지 호출별 제한인지는 총괄 정책을 확인해야 한다. 삽입한 `;` 포함 event 문자열은 실행되지 않았으나 게임 ID로 허용됐다. 실제 전송·worker 동작은 확인하지 않았다.

#467의 보존 수집 표본은 1경기·예고 선발 2행이며 둘 다 probable이고 외부 수신 인증 false다. 합성 원문을 실제 어댑터와 queue에 연결했을 때 이 불완전 자료는 rejected로 남아 새 작업을 만들지 않았다. 최종 어댑터 head가 준비되면 이 모든 반례와 37개 드라이버 시나리오를 다시 실행해야 한다.

## 개발 중 어댑터의 합성 반례

읽기 전용으로 복제한 `fact_delta_inputs.py` 스냅샷 SHA256 `19e7dc3fe51502e1c558f1dce342a1068b1b0fbb8631f68d06ec23c33274a7e4`을 `vendor/fact_delta_snapshot.py`로 보존하고 실행했다. 개발 도중 버전이므로 이후 수정본이나 최종 PR에 그대로 적용되는 결론은 아니다.

- 정상 core와 빈 사실 목록에서는 원 baseline 확률을 보존하고 외부 수신 인증을 false로 반환했다. 사실 입력이 유효한 경우에도 외부 인증 여부를 false로 남겼다. raw hash와 확인 플래그는 함수 호출자의 주장이고 실제 HTTP 원문이나 외부 수신 증거를 검사한 것은 아니다.
- 선수 ID가 빠진 사실을 주면 `InvalidFact`를 발생시켰다. 같은 core에서 빈 사실을 별도로 호출하면 baseline은 그대로였다. 즉 이 스냅샷 자체는 사실만 무효일 때 baseline을 자동 반환하지 않는다. 상위 호출자가 오류 종류를 구분해 유효한 core에 한해 안전하게 대체할 수 있는지는 아직 확인하지 못했다. 경기·상품·시점 등 core 오류까지 fallback하라는 뜻은 아니다.
- 합성 `confirmed_starter_change`의 이전 값과 이후 값을 동일한 확정 선수·상태로 주어도 feature가 생성됐다. 실제 변경으로만 연구를 깨우려면 원문 사실의 semantic 비교와 신규 event 생성 경계에서 이를 거부하거나 변화 없음으로 처리해야 한다. 이 스냅샷은 어댑터이지 대기열이 아니므로 실제 중복 dispatch가 발생했다는 뜻은 아니다.
- 합성 경기 결과 필드 주입, 다른 상품, 결정 이후 공식 자료 수신은 거부됐다. 이는 테스트한 형태의 경계 확인이며 다른 누출 경로 전체를 증명하지 않는다.

## 대기열·수집기 검증 준비

`conformance-scenarios.json`에 37개 독립 시나리오를 명시했다. 사전 수신과 게시 주장 분리, probable/confirmed, 선수·경기·상품 ID, raw hash 검증과 독립 수신 인증 분리, 사실과 의견 분리, postgame 결과 차단, 기준 확률 보존을 다룬다. 대기열에서는 generated_at만 변경, 동일 내용 재입력, 과거 445경기 재열람, 리그 간 ID namespace, 같은 ID의 다른 신원·리비전 충돌, 최초 수신 시각 소급, 유일한 새 리비전, 정확한 워커 라우팅, 명시적 재시도 가능 실패 후 재계획·성공 후 중복 계획 방지, 수신 불확실 시 재전송 보류, prompt/thread ID 및 명령 문자열 주입을 다룬다.

각 시나리오는 설명·순차 단계·관찰해야 할 결과로 구성된다. 실행에 필요한 실제 객체와 호출은 **추후 확정된 코드에 맞춰 격리된 테스트 드라이버로 작성해야 한다**. `run_fixtures.py`는 그 로컬 Python 드라이버를 매 시나리오마다 별도 임시 디렉터리에서 shell 없이 실행하고 JSON 결과를 검사한다. 이는 네트워크를 차단하는 샌드박스가 아니므로 운영 서비스나 실제 데이터에 연결된 드라이버를 사용하면 안 된다. 37개 전체를 일괄 실행하는 드라이버는 작성하지 않았다. 위 후속 검토의 개별 Python 테스트가 실제 수집기와 대기열의 일부 시나리오를 실행한 범위만 확인했다.

몇 가지 기대는 확인이 필요한 인터페이스 가정이다. 예를 들어 probable 자체를 별도 유효 사실로 보관할 수 있지만 `confirmed`를 요구하는 후보나 dispatch 조건에서는 확정으로 취급하지 않는다. 유효한 확정 사실과 같은 상품 가격이 있다면 학습 모델이 없어도 연구 입력은 ready이며 예측 확률은 baseline을 유지한다. 같은 식별자 문자열도 공식 리그 namespace가 다르면 구분해야 한다. 동일 semantic 이벤트의 재수신과 수정된 사실의 새 revision은 서로 다르다. CLI는 실제 메시지를 보내지 않고 계획과 ack만 처리한다. 전달 수신 여부가 불명확하면 uncertain으로 남겨 자동 재전송하지 않는다. 중복 억제와 재시도는 계획 횟수뿐 아니라 durable 상태와 실패 지점별 side effect까지 최종 구현에서 확인해야 한다.

## 상태와 제한

이번 검토에서 신규 전향 공식 사실은 **직접 수집하지 않았고**, #467이 보존한 예고 선발 2행만 읽었다. 적중률·ROI 평가는 실행하지 않았다. 합성 테스트는 모델 수익성, 독립 영수증, 실제 실행 가격, raw source 진위를 증명하지 않는다. 예상 스케줄·기회가 없는 것을 실제 수집 결과 0으로 혼동하지 않는다.

최종 collector/adapter/queue head와 실제 인터페이스가 제공되면, 그 commit 및 입력 해시를 기록하고 각 시나리오의 드라이버를 구현해 격리 환경에서 다시 실행해야 한다. 원본 worktree·운영·DB·스케줄러는 변경하지 않았다.
