# 증설 없는 운영을 위한 보조 작업 시작 제어

## 변경

- supervisor의 기존 무거운 작업 잠금을 재사용한다. 잠금 획득 후 Linux
  MemAvailable이 기본 512MB 이상일 때만 보조 작업을 시작한다.
- 메모리가 부족하거나 측정할 수 없으면 잠금을 풀고 30초 뒤 다시 검사한다.
  대기 중 자식 프로세스나 새 작업을 계속 생성하지 않는다.
- 최초 대기와 이후 5분마다 여유 메모리, 기준, 대기 시간을 기록한다.
  실제 실행 시점도 따로 기록한다. 작업 성공으로 가장하거나 기존 산출물을 비우지 않는다.
- 선수 정보, 공개 픽스터, 날씨, 야구 컨텍스트, 추천 재계산, 산출물 계산,
  일일 xG, 부팅 후 과거 데이터 이관에 적용한다.
- HTTP, 실시간 점수, 실시간 배당, 기본 배당 스냅샷은 이 제한 밖이다.
  실시간 수집 주기와 예측 기준은 변경하지 않는다.
- 실행 중 작업 강제 종료/일시 정지는 하지 않는다. DB 트랜잭션을 잡은 작업을
  임의 중단하면 안전하지 않으므로 시작 시점의 허용 여부만 제어한다.

## 기준과 한계

운영에서 배당 약 220~250MB, 점수 약 200MB, API 약 150MB와 보조 계산
약 280~320MB가 겹쳐 OOM이 재현됐다. 512MB는 시작 여유를 보수적으로 잡은
초기값이며 프로세스 메모리 상한이나 512MB의 강제 예약이 아니다.
BACKGROUND_MIN_AVAILABLE_MB 환경변수로 조정할 수 있지만, 증거 없이 낮추지 않는다.

메모리가 계속 부족하면 보조 작업은 계속 대기할 수 있고 추천/분석이 낡을 수 있다.
실시간 작업끼리 또는 시작 이후 작업이 커지는 경우의 OOM까지 막지는 못한다.
Linux /proc의 머신 가용량 기준이며, 별도 컨테이너 cgroup 메모리 제한이 더 작은
환경으로 이전한다면 해당 제한을 반영하도록 바꿔야 한다.

PR #225의 전체 이벤트 적재 제거와 병행 검증해야 한다. 파일이 겹치지 않도록
이 PR은 supervisor와 별도 테스트만 수정했다. #225를 포함하거나 배포한 것은 아니다.

## 검증 및 운영 적용

- Python 770 passed, 58 subtests passed.
- 낮은 메모리/측정 실패시 대기, 회복시 시작, 대기 중 잠금 해제,
  작업 예외시 잠금 해제, 실시간 수집 우회, 이관 제어, 산출물 순서 유지 테스트.
- 웹 232개 테스트 및 프로덕션 빌드 확인.
- 운영 적용 전이다. 유료 증설/재시작/병합/배포는 하지 않았다.
- 배포 승인 후 최소 전체 계산 주기를 포함해 OOM과 HTTP 지연뿐 아니라
  실시간 최신성, 보조 작업 대기 시간과 완료 여부를 확인해야 한다.
  대기가 무한히 지속되는 것을 안정화 성공으로 판정하지 않는다.
