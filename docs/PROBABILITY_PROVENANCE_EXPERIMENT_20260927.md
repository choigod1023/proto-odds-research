# 확률 출처·동시점 후보 기록과 단순 보정 실험

## 이번 변경 범위

운영 픽 선택 공식은 변경하지 않는다. 확률 보정은 오프라인 실험으로만 실행한다.
추가한 수집 코드는 배포 후 신규 기록부터 적용되며, 기존 기록을 소급 보완하지 않는다.

- 추천 이력에 시장 확률, 사용 확률, 확률 출처, 적용 모델/decision ID/hash 등을 보존한다.
- 가상 비교에 경기별 전체 연구 후보를 저장한다. 기존 baseline/challenger 선택 로직은 그대로다.
- 동일 생성·원천·배당·관측 시각의 batch ID를 저장한다. 첫 관측 후보를 이후 픽으로 교체하지 않는다.
- 공식 결과가 들어오면 저장한 후보 각각의 원래 선택과 배당을 기준으로 정산한다.
- 로컬 평가기는 같은 경기에서 픽을 바꾸는 비교와 동일 batch 내 서로 다른 두 경기 조합을 지원한다.

## 실제 데이터 감사

앞선 PR #245와 동일한 원본 스냅샷을 사용했다. API를 새로 조회해 더 좋은 결과를 찾지 않았다.
후속 추천 응답 생성 시각은 2026-09-27 10:20:47 KST다.

- 과거 추천 이력 1,101건: 확률 출처 미보존. 미상으로 분류한다.
- 해당 응답의 현재 후보 71건: 모두 shin_market_fallback.
- 기존 가상 비교 125건의 baseline 출처: 모두 shin_market_fallback.
- 완전한 대안 후보 기록: 0건. 지금의 배당이나 후보를 과거에 끼워 넣지 않는다.

현재 후보의 출처가 같다는 이유로 과거 1,101건도 모두 같은 출처였다고 주장하지 않는다.
출처 미상 자료로 검증된 모델의 우위를 증명할 수도 없다.

## 단순 확률 보정 결과

9월 25일 13:27:49 UTC에 확보한 스냅샷의 공식 정산 추천 354건으로
`sigmoid(a * logit(p) + b)`를 학습했다. 계수는 a=1.275891, b=-0.155360이다.
손실은 이진 로그 손실 합 + (a-1)^2 + b^2다. a는 0~5, b는 -5~5로 제한했다.
규제 강도·배당 기준을 신규 결과로 최적화하지 않았다. 이번에 설계한 탐색적 실험이지 사전 등록 검증은 아니다.

이전 스냅샷에 없고 게시·기록 시각이 모두 이후인 신규 정산 23건에서:

- Brier 오차: 0.259012 → 0.255733, 약 1.27% 감소.
- 로그 손실: 0.711364 → 0.704680, 약 0.94% 감소.
- 기존 확률 60%·배당 1.50 이상: 4건 중 3건 적중, +0.51단위, ROI +12.75%.
- 보정 확률 × 배당 - 1 ≥ 3%: 선택 0건. ROI는 0%가 아니라 미산정.

과거 내부 시계열 확인에서는 반대 결과가 나왔다.

- 9월 15일 경계 이후 185건: Brier 0.244113 → 0.245804로 악화.
- 9월 19일 경계 이후 107건: Brier 0.240167 → 0.240938로 악화.

내부 구간은 서로 겹치므로 독립 실험 두 번으로 세지 않는다. 학습에는 경계 이전에
정산 시각이 기록된 자료만 사용한다. 새 배당으로 정산을 갱신하면서 과거 결과 가용 시점을
잃은 경우는 과거 학습 자료로 억지 복원하지 않는다.

판단: 신규 구간의 오차 개선은 작고 내부 구간에서 일관되지 않다. 수익률 개선도 확인되지 않았다.
운영 확률 보정으로 승격하지 않는다. 선택된 픽만으로 학습했으므로 탈락한 모든 시장 후보에
이 보정이 통한다는 주장도 하지 않는다. 시장 대비 추가 경기 정보 모델은 필요한 시점별 입력과
출처가 충분히 확보되기 전까지 학습·우위 검증 완료로 표시하지 않는다.

## 같은 경기·조합 재검증 규칙

비교용 정책은 실제 베팅 추천이 아닌 `paper-max-saved-ev-price150-220-v1`이다.
동일 기록 내 1.50 ≤ 배당 < 2.20 후보에서 저장 확률 × 배당 - 1이 가장 큰 후보를 고른다.
동률이면 저장 확률, 선택 키 순으로 결정한다. 정산 결과는 선택에 사용하지 않는다.
baseline이 동일 가격으로 후보 목록에 존재하고 같은 배당 범위에 들어온 경기만 양쪽 모두 비교한다.
따라서 같은 경기 수의 비교이지만 모든 경기의 커버리지를 유지한다고 주장하지 않는다.
저장 확률의 우위가 검증되지 않았으므로 최대 저장 EV도 양의 실제 기대수익을 뜻하지 않는다.

조합은 같은 batch의 경기들을 시작 시각·ID 순으로 정렬하고 겹치지 않는 두 경기씩 묶는다.
서로 다른 batch를 조합하거나 결과를 보고 상대 경기를 고르지 않는다.
무효 leg는 배당 1로 정산하며 모든 leg가 공식 정산되기 전에는 대기로 남긴다.
두 방식의 정산 완료 집합이 다르면 전체 ROI와 양쪽 모두 정산된 공통 표본 차이를 분리한다.

현재 원본의 완전한 후보 기록은 0건이므로 같은 경기 대안 비교와 조합 ROI는 미산정이다.
양의 조합 수익률을 보이는 단위 테스트는 정산 공식을 확인하는 합성 사례이지 실제 성과가 아니다.

## 기록 상한과 비용 측정

- 경기당 후보 최대 24개. 초과 시 일부를 고르지 않고 전체 대안 기록을 보류한다.
- 신규 proposal batch 후보와 누적 보존 후보에 각각 256KiB 직렬화 예산을 적용한다.
- 예산 계산은 ASCII JSON 크기 + 후보당 256바이트의 정산 필드 여유다. Python 객체/RSS 상한은 아니다.
- 용량 소진 후 기존 결과를 지우지 않는다. 신규 대안은 `archive_budget_exhausted`로 남기고
  기존 baseline/challenger 비교는 계속한다. 첫 관측에 없던 후보를 나중에 채우지 않는다.
- 상한 때문에 완전한 후보를 가진 기간/경기만 분석할 수 있다. 표본 누락 사유를 함께 출력한다.

로컬 Python tracemalloc로 300경기 × 4후보, 신규 상태 생성 한 번을 비교했다.
입력 목록은 측정 전에 만들었으며 전체 프로세스 RSS나 장시간 실행 측정은 아니다.

- 변경 전: 0.0326초, Python 최대 할당 513,150바이트, 상태 JSON 254,928바이트.
- 변경 후: 0.1035초, Python 최대 할당 1,205,424바이트, 상태 JSON 477,536바이트.
- 완전한 후보 기록 85경기, 예산 예약 261,585바이트에서 상한 작동.

추가 Python 최대 할당은 약 0.66MiB였지만, 실제 데이터의 문자열 길이와 기존 이력에 따라 달라진다.
운영 메모리 문제가 해결됐거나 이 변경이 무비용이라고 해석하지 않는다.
