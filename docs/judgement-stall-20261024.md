## 확인된 결함과 최소 수정

`_run_odds_cycle`은 `_odds_recommendation_lock`을 잡고 배당 수집 자식을
`subprocess.run`으로 기다리지만 전체 실행 제한이 없었다. 소켓 read timeout은
응답 전체의 완료 시간을 제한하지 않는다. 수집 자식이 끝나지 않으면 독립 판정
복구도 같은 잠금을 획득하지 못하며, optional 작업도 pending 상태로 대기한다.

수집에 900초 상한을 추가했다. 평소 주기 60초는 실행 제한이 아니라 종료 후
대기 시간이다. 900초는 정상 전체 회차 스캔에 여유를 두기 위한 운영 상한이며
실측 최적값이라고 주장하지 않는다. 시간 초과 시 subprocess.run이 자식을 종료하고
회수한 뒤 기존 finally가 잠금과 pending 상태를 해제한다. 기존 looper는 실패로
기록하고 60초 후 재시도한다. 실패한 수집을 성공으로 취급하거나 게시하지 않는다.
DB 기록·마지막 정상 산출물·추천 정책·메모리 admission 기준은 변경하지 않았다.

실제 로컬 Python 자식(1초 대기)에 0.2초 제한을 적용하는 회귀 테스트와,
실패 후 60초 재시도 및 잠금 해제 테스트를 추가했다. 변경 전 두 테스트 실패,
변경 후 관련 테스트 67개 통과. 이 재현은 운영 장애 원인을 확정하는 증거가 아니다.

## 디스크 및 남은 확인 사항

- 300MB 기준은 collector_watchdog의 경보 조건이다. supervisor가 디스크 49MB를
  이유로 판정을 직접 차단하는 조건은 없다. 여유가 남았더라도 한 트랜잭션의 추가
  DB/WAL 쓰기에 부족할 가능성은 있으나 현재 ENOSPC를 확정할 수 없다.
- 원문 회차 HTML은 documents에 JSON 문자열로 비압축 저장되고 동일 회차는 갱신된다.
  모든 HTML이 무조건 무한 추가된다고 해석하면 안 된다.
- odds_snapshots와 append-only 원장은 누적 보존된다. 무단 삭제하거나 과거 원장을
  제거하는 수정은 하지 않았다.
- SQLite WAL 모드이며 기본 자동 체크포인트를 임의로 끄는 코드는 없다. 오래 열린
  reader에 따른 WAL 증가 여부는 파일 크기와 실제 reader 확인이 필요하다.
- 판정 실패 시 market_retry가 유지되면서 새 원천 수집을 생략하는 경로가 있다.
  따라서 배당·판정 동시 정체가 반드시 수집 자식 hang을 의미하지는 않는다.
- 메모리 512MB admission, 판정 300초 제한, DB 쓰기 오류, source 실패를 구분하려면
  오류 로그와 DB 본체/WAL/SHM 및 git 객체의 크기, 프로세스와 메모리 상태가 필요하다.

지우지 않는다. 이 변경은 전체 정체 원인 해결이나 배포 완료가 아닌, 확인된
