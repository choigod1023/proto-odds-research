# 선수 입력·캐시 후속 검증

운영 조회 기준: 2026-09-27 09:39~09:45 KST 부근. 운영 코드는 #243의
1f029192이며, 이 문서의 후속 수정은 아직 운영에 적용하지 않았다.

## 운영에서 확인한 사실

- 목록 generated_at 09:28:03 / revision 09:30:55가 health의 picks 생성/저장
  시각과 일치했다. 이전 목록 반영 지연은 이번 관측에서 해소됐다.
- 선수 문서는 9/26 21:56:00 생성, 21:56:13 저장 이후 그대로였다.
  최근 로그에서 선수 수집 대기 6,396초를 확인했다. 한 번의 정상 종료가
  지속적인 최신성 확보를 보장하지 않는다.
- 원장 예측은 2,781→2,801, 정산은 73→95로 증가했다.
- #243 배포 후 새 예측 20건 모두 research_player_inputs가 unavailable이며
  이유는 missing_or_ambiguous_fixture였다. 연구 입력 확보율은 0/20이다.
- 그중 KBO 4경기는 선수 문서에 존재하지만 시각이 `2026-09-27T17:00:00`으로
  저장됐다. 예측 kickoff는 UTC 08:00이다. 이 네이버 KBO 로컬 시각이
  SQL에서는 UTC로 취급되고 Python에서는 시간대 불명으로 거부됐다.
- 해당 KBO 원천 관측은 9/26 11:34:13 UTC이다. 매칭을 고쳐도 예측 당시
  6시간 기준을 넘었으므로 신선한 입력으로 인정하면 안 된다.

## 재현 및 수정

1. KBO 시간대: 수정 전 재현 테스트 2개 실패. 알려진 네이버 KBO의 초 단위
   로컬 시각만 +09:00으로 해석하고 DB 조회와 capture가 같은 함수를 쓴다.
   임의 출처의 시간대 추측, 날짜만으로 매칭, 중복 임의 선택은 하지 않는다.
2. 캐시: 같은 초에 선수 정보만 변경해 저장하면 stored_at이 같아 캐시가 갱신을
   놓치는 별도 결함을 재현했다. 쓰기 트랜잭션 안에서 마이크로초 단위의
   증가하는 저장 버전을 할당한다. 원천 generated_at은 변경하지 않는다.
   이 결함이 과거 운영 캐시 지연의 유일한 원인이라는 증거는 없다.
3. 통합 테스트: 임시 SQLite 조회→신선한 선수 입력 capture→사전 원장 저장→
   후속 정보가 고정 입력을 바꾸지 않음→공식 결과를 동일 스냅샷에 정산→
   재정산 중복 방지까지 실제 Python 실행으로 검증했다. 모의 데이터 결과다.

## 남은 조건

- 메모리 대기로 선수 수집이 반복 지연되는 문제는 이 수정의 해결 범위가 아니다.
  gate를 낮추거나 운영 데이터를 소급 수정하지 않았다.
- 과거 20개 고정 예측은 덮어쓰지 않는다. 수정 적용 뒤 신선한 자료가 있는
  새 경기에서 captured 기록을 확인해야 운영 입력 연결 성공으로 판단한다.
- training_eligible=False와 affects_probability=False를 유지한다.
  이 테스트를 적중률·ROI 개선의 증거로 사용할 수 없다.
- 운영 변경 전에는 CI, 병합 및 배포 승인과 적용 확인이 필요하다.
