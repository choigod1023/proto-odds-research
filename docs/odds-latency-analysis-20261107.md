# 2026-11-07 배당 갱신 지연 분석

운영 앱은 proto-odds-collector, 체크아웃은 0a8e237b이며 shared-cpu-1x / 1024MB 구성이다. 기존 작업의 로그와 /proc, 읽기 전용 SQLite 질의, 기존 압축 응답 스냅샷을 확인했다. 비교 실행은 격리된 로컬 SQLite에서 수행했다.

## 운영에서 확인한 지연

- 12:28:29 KST에 새 배당을 DB에 저장했다.
- 판정 슬롯 60초 대기 실패와 다른 판정의 300초 타임아웃 이후 재시도했다.
- 12:35:34부터 성공한 판정의 누적 단계 시각은 입력 읽기 38.9초, 판정 완료 90.5초, 정산 완료 180.3초, 원장 처리 완료 190.0초, 저장 완료 227.0초였다. 각 수치는 단계 시작 이후의 누적 경과 시간이다.
- 다음 웹 응답 준비는 95.51초 걸렸고 12:41:10에 게시했다. 배당 DB 저장에서 게시까지 12분 41초였다.
- 같은 작업 구간의 원장 규모는 11,580행 / JSON 합계 80,471,619자, picks_v2는 약 39.6백만 자였다.
- 12:45:14에 커널이 Python PID 12883을 OOM으로 종료했다. 당시 anon-rss는 454,928KB였다. 이어 KBO 후속 작업의 180초 타임아웃이 기록됐으며, 이 시간적 인접성만으로 단독 원인을 확정할 수는 없다.

## CPU 배정 관측

10.155초 동안 /proc/stat 차이는 user 69, system 14, iowait 64, steal 908 ticks였다. 합계에 대한 steal 비율은 86.07%, iowait는 6.07%였다. 같은 PID의 판정 프로세스는 그동안 CPU 0.78초를 받았고 RSS는 380,592KiB였다.

13:08:12 KST에 끝난 두 번째 10초 관측에서는 steal 92.84%, iowait 0%였으며 MemAvailable은 487,620KiB(약 476MiB)였다. 두 짧은 관측 구간의 결과이며 하루 전체의 CPU 배정이나 최대 메모리를 입증하는 값은 아니다.

Fly 공식 문서는 shared vCPU의 기본 할당을 80ms당 5ms(6.25%)로 설명한다. 남은 burst balance를 사용하면 더 실행할 수 있다. steal에는 quota 초과에 따른 throttling과 같은 호스트의 자원 경쟁이 모두 포함되므로, 이번 /proc 관측만으로 둘의 비중이나 burst balance를 확정하지 않는다.

출처는 [Fly CPU Performance](https://docs.fly.io/machines/cpu-performance)이며 2026-11-07에 확인했다.

## 로컬 비교 방법과 결과

추가로 12:17 생성 목록과 12:28 배당에 대한 게시 스냅샷을 경기 식별자로 대조했다. team_form_display가 달라진 109경기는 전부 form_before 기준시각만 달랐으며 실제 성적 값은 같았다. 이전 코드는 이 시각 변화도 changed로 세어 전체 산출물 저장과 응답 재준비를 유발할 수 있었다. 수정 후에는 실제 표시 값이 달라질 때 기존 기준시각을 갱신한다. 실제 새 성적이나 배당·픽스터 변화의 게시 경로는 회귀 테스트로 함께 확인했다.

/data/proodd.responses.zip에 이미 게시된 압축 상세 3,296경기를 다운로드했다. all scope의 live/past 소속을 유지하고 상세를 복원한 뒤 로컬 DB 한 개에 넣었다. 운영 원장 전체나 학습 모델을 실행한 비교는 아니다.

기존 구현과 변경 구현을 각각 새 Python 프로세스에서 실행했다. recent/all/performance JSON과 모든 상세의 정규화 SHA-256이 일치했다. 측정은 Windows Python 3.14의 프로세스 최대 working set이며 운영 Linux의 성능을 직접 예측하지 않는다.

처음 시도한 SQLite 경기별 조회는 기존 2.05초 / 383.8MB에서 2.44초 / 410.5MB로 악화되어 제외했다.

채택한 수정은 JSON 전체의 추가 문자열·바이트 복사본 없이 기존 청크 인코더에서 gzip으로 바로 전달한다. gzip 수준 3을 유지한다. 같은 비교의 결과는 다음과 같다.

- 기존 전체 응답 생성은 wall 2.103초, CPU 2.109초, 최대 RSS 383,905,792 bytes였다.
- 수정 후에는 wall 1.973초, CPU 1.953초, 최대 RSS 274,165,760 bytes였다.
- 최대 RSS는 약 104.7MiB(28.6%) 감소했다. 이 한 번의 측정에서 wall 시간은 약 6.2% 줄었다.
- 압축 크기는 all 4,074,687 bytes, performance 1,118,861 bytes, recent 748,364 bytes로 두 구현이 같았다.
- 의미적 해시는 두 구현 모두 18c942b2315250476e7cc28882eb5626c5d879b1dda1bf2a9048fc45478417cc였다. 로컬 DB의 새 revision 때문에 다음 실행의 해시 자체는 달라질 수 있으며, 매 실행 내 두 변형의 일치를 확인한다.

재현 명령은 python scripts/benchmark_match_response_build.py --snapshot <downloaded-responses.zip> --baseline 0a8e237b 이다. 다운로드한 운영 자료는 커밋하지 않는다.

## 후속 운영 검증

판정 단계 로그에 누적 CPU 시간을 추가했다. 배포 후 단계별 wall/CPU/RSS와 응답 게시까지의 시간을 다음 자동 주기에서 다시 대조해야 한다. 이번 변경의 운영 지연 감소량은 아직 측정하지 않았다.

우선순위는 응답 생성의 메모리 감소 확인, 반복되는 전체 원장·과거 경기 처리의 CPU 비용 축소, 배당·판정 슬롯 적체 재측정 순이다. CPU 대기가 계속 높으면 CPU quota/burst/throttling 지표를 함께 확인해 자원 변경 필요성을 판단한다.
