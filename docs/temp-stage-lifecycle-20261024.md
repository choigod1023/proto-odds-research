# Stage / publish 임시 디렉터리 누적 조사

## 확인된 결함

`DatasetStore.replace_datasets_records`는 DB 옆에 `proodd-stage-*`를 만들고
`TemporaryDirectory` 종료에만 정리를 맡겼다. supervisor의 충돌 복구 publish도
`collector-publish-*` worktree를 만들고 `finally`에서만 정리했다.
OOM/SIGKILL/머신 종료에서는 두 정리 코드 모두 실행되지 않는다. 재실행 시
잔여물을 회수하는 경로도 없었다. 예외에 의한 정상 스택 해제와 강제 종료를 구분해야 한다.

부모 작업이 전달한 운영 관측은 /data 여유 약 50MB, stage 약 35개(각 80~185MB),
publish 약 539MB다. 이 작업은 운영에 접속하거나 파일을 지우지 않았다.
이 누적 결함은 확인했지만 현재 판정 실패가 ENOSPC 때문인지까지 확정한 것은 아니다.
원장 충돌, DB 압축/삭제, releases 정리는 범위 밖이다.

## 수정과 안전 경계

- 새 scratch 공간에 종류·이름·부팅 ID 표식과 프로세스 수명 파일 잠금을 둔다.
- stage 생성 직전 동일 부모 아래 소유 표식이 있는 종료된 stage만 회수한다.
  SQLite staging은 소유 프로세스만 사용하므로 비차단 잠금 획득으로 종료를 확인한다.
- publish checkout은 잠금 표식 디렉터리 안의 `checkout`에 생성한다.
  Git 자식이 부모보다 오래 살아 있을 수 있으므로, publish 잔여물은 **다른 Linux
  boot ID**와 잠금 해제를 모두 확인한 다음 publish 시도에서만 회수한다.
  같은 부팅에서 남은 publish는 보수적으로 유지한다. 즉시 회수 보장이 아니다.
- 활성 잠금, 미확인 부팅, 손상/누락 표식, symlink/junction은 건너뛴다.
  stage에 예상하지 못한 파일(예: 원장 DB)이 있어도 건너뛴다.
- 기존 무표식 디렉터리는 자동 채택/삭제하지 않는다. 라이브 DB 경로와 repo/releases는
  삭제 대상이 아니다. Git의 전체 `worktree prune`도 실행하지 않는다.
  강제 종료된 publish의 소량 Git 관리 메타데이터는 별도 수동 검토 대상으로 남는다.
- 표식 생성 도중 강제 종료되거나 정리 권한이 없으면 보수적으로 잔여물이 남을 수 있다.

## 기존 잔여물에 대한 별도 정리 절차 (이번 작업에서 실행하지 않음)

1. 정확한 절대 경로·크기·파일 종류 목록을 읽기 전용으로 저장한다.
2. 부모/자식 프로세스의 cwd, 열린 fd, Git worktree 등록을 함께 대조한다.
   나이, PID 부재, 디렉터리 접두사만으로 종료를 판정하지 않는다.
3. 과거 stage가 재시작 전부터 존재했고 새 코드가 이를 재사용하지 않는다는 증거와
   라이브 DB/WAL/원장이 아니라는 확인을 얻는다. 불명확하면 보존한다.
4. 운영 담당자가 동시 생성/재사용 가능성을 통제할 수 있는 시점과 별도 삭제 승인을
   확보한 뒤, 확인된 개별 경로만 정리한다. `/data` 전체나 와일드카드 삭제는 금지한다.
5. 여유 공간, 원장 보존, 다음 정상 수집/판정 게시를 검증한다.

현재 쌓인 수GB가 이 코드 배포만으로 즉시 비워진다고 보고하면 안 된다.

## 로컬 검증

자식 Python 프로세스가 stage에 1MB DB를 쓴 뒤 `os._exit(9)`로 종료한다.
실제 잔여물을 확인한 후 다음 workspace 진입에서 회수되는 것을 테스트했다.
활성 잠금·원장 파일·기존 무표식·손상 표식 보존, 정상 예외 정리,
publish 부팅 경계, Git worktree 부분 생성 실패 정리도 회귀 테스트에 포함했다.
Windows에서 symlink 생성 권한이 없어 해당 테스트는 skip하며 Linux CI에서 실행한다.
운영 삭제/재시작/배포는 수행하지 않는다.
