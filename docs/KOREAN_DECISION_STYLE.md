# 수치 판정 한국어 문체

이 프로젝트는 경기 결과를 보장하지 않는다. 대신 데이터로 계산한 값과 그 값에
따른 선택은 분명하게 말한다.

> 확률은 숫자로 말하고, 계산 결과와 추천 결정은 단정형으로 말한다. 추정형은
> 실제로 데이터가 없거나 아직 확정되지 않은 항목에만 쓴다.

## 기본 문체

- 분석과 판정은 간결한 `한다체`로 쓴다.
- 버튼 사용법처럼 독자에게 행동을 요청할 때만 `~하세요`를 쓴다.
- 한 화면에서 `한다체`, `합니다체`, `해요체`를 섞지 않는다.
- 번역투와 이중 피동을 피하고 주체를 드러낸 능동문을 쓴다.
- 한 문장에는 한 가지 판단만 둔다. 확률, 선택, 제외 사유를 긴 문장 하나로
  엮지 않는다.

## 문장 등급

### 1. 확인된 사실

관측값과 확정 정보는 단정형으로 쓴다.

- `인천은 최근 6경기 무패다.`
- `전반 기준점은 1.5골이다.`
- `확정 선발에 마테우스와 이동률이 포함됐다.`

`~로 보인다`, `~인 듯하다`, `~일 가능성이 있다`를 붙이지 않는다.

### 2. 모델 계산

확률값 자체가 불확실성을 나타내므로 말끝에서 다시 흐리지 않는다.

- `모델은 인천 승리 확률을 63.8%로 계산했다.`
- `오버 확률은 54.2%다.`
- `보수 기대수익은 -8.4%다.`

`승리할 가능성이 63.8%로 보인다`처럼 숫자와 완곡어법을 겹치지 않는다.

### 3. 정책 결정

조건을 통과한 선택과 제외 결정은 확정형으로 쓴다.

- `최종 선택은 인천 승이다.`
- `오버를 추천한다.`
- `기대수익 기준에 미달했다. 추천하지 않는다.`
- `전반전 시장은 모델이 계산하지 않았다. 추천에서 제외한다.`

추천의 확정성과 경기 결과의 확정성을 혼동하지 않는다. `최종 선택은 인천
승이다`는 서비스가 내린 결정을 뜻한다. `인천이 반드시 이긴다`는 결과 보장이므로
쓰지 않는다.

### 4. 미확정 정보

실제로 확인되지 않은 정보만 상태를 명시해 남긴다.

- `공식 선발 명단이 아니다. 명단 발표 뒤 다시 계산한다.`
- `투표량 자료가 없어 실제 쏠림은 판정하지 않는다.`
- `결장 영향값이 없다. 이 변수는 계산에서 제외했다.`

`변수가 될 수 있다`처럼 무엇을 어떻게 처리했는지 알 수 없는 문장은 쓰지 않는다.

## 권장 문장 순서

추천 설명은 결론부터 쓴다.

```text
최종 선택은 인천 승이다.
모델 확률은 63.8%, 시장 확률은 57.1%다.
모델과 시장의 확률 차는 +6.7%p다.
추천 기준을 통과했다.
```

추천하지 않을 때도 같은 순서를 쓴다.

```text
추천하지 않는다.
모델과 시장의 확률 차는 -1.2%p이고 보수 기대수익은 -8.4%다.
두 값 모두 추천 기준에 미달했다.
```

## 판정 범위와 시점

서로 다른 계산을 한 단어 `추천`으로 합치지 않는다.

- `경기 모델과 일치`: 경기별 모델 추천과 오늘 조합의 시장 선택이 같다.
- `시장 수치만`: 시장확률과 배당구간 실측값으로 고른 선택이며 경기 모델 추천은 아니다.
- `경기 모델 미계산`: 해당 마켓의 모델확률이 없다.
- `경기 모델 추천 제외`: 모델확률은 있지만 추천 기준을 통과하지 못했다.

실시간 배당과 산출물의 시점도 구분한다. 저장된 해설은 `산출 시점의 최종 선택은
인천 승이다`라고 쓰고, 실시간 배당으로 자격을 잃으면 `현재 배당 기준 경기 모델
추천은 제외됐다`라고 갱신한다. 산출 시점 배당을 현재 배당처럼 쓰지 않는다.

## 바꿔 쓰기

| 피할 표현 | 사용할 표현 |
| --- | --- |
| `A가 유리해 보인다` | `모델은 A 우세로 판정했다` |
| `A의 승리가 예상된다` | `최종 선택은 A 승이다` |
| `오버 가능성이 있다` | `오버 확률은 62.4%다. 오버를 추천한다` |
| `추천을 보류하는 편이 좋다` | `추천하지 않는다` |
| `가치가 낮아 보인다` | `기대수익이 기준에 미달했다. 제외한다` |
| `모델과 시장이 엇갈리는 것으로 보인다` | `모델과 시장이 엇갈린다` |
| `선발이 변수가 될 수 있다` | `공식 선발이 아니다. 발표 뒤 다시 계산한다` |

## 참고한 공개 지침

- [GitHub Docs 문체 가이드](https://github.com/github/docs/blob/main/content/contributing/style-guide-and-content-model/style-guide.md):
  명확하고 단순하며 자신 있는 문장과 능동태를 권장한다.
- [GitHub 번역 대상 문서 작성 지침](https://docs.github.com/ko/enterprise-cloud@latest/contributing/writing-for-github-docs/writing-content-to-be-translated):
  직설법을 쓰고 모호한 조동사와 장황한 표현을 줄이도록 안내한다.
- [Kubernetes 한국어 현지화 가이드](https://github.com/kubernetes/website/blob/main/content/ko/docs/contribute/localization_ko.md):
  객관적인 평어체를 기본으로 하고 번역투와 이중 피동을 피한다.
- [Microsoft 한국어 현지화 스타일 가이드](https://download.microsoft.com/download/5/b/6/5b62389f-4e3b-4c77-bc18-94efba2fa7bb/kor-kor-StyleGuide.pdf):
  짧고 읽기 쉬운 문장과 명확한 능동 표현을 권장한다.
- [Google 개발자 문서 Voice and tone](https://developers.google.com/style/tone):
  독자에게 직접 말하고 자신 있는 어조를 사용하도록 안내한다.
