# 메모리 보관·중복 처리 수정

## 확인한 원인

- supervisor의 산출물 응답 캐시는 압축본뿐 아니라 큰 UTF-8 원본도 계속 보관했다.
- 캐시 검사 이후 DB 읽기와 압축을 잠금 밖에서 수행해 동시 요청이 같은 갱신을 중복 처리할 수 있었다.
- 목록 응답 준비 작업과 산출물 요청의 큰 JSON 처리도 겹칠 수 있었다.
- 점수 수집기의 팀명 매칭은 sport/date/home/away만 사용하는데 전체 picks_v2를 역직렬화해 보관했다.

이는 확인된 불필요한 보관과 동시 할당 경로다. 운영 RSS 증가 전부가 메모리 누수라는 증거는 아니다.

## 변경

1. 산출물 응답은 압축본과 실제 revision만 보관한다. 비압축 요청에서만 일시적으로 해제한다.
2. 큰 응답의 준비는 하나만 수행한다. 동시에 온 요청에는 마지막 정상 응답을 보내고, 아직 정상 응답이 없으면 503으로 재시도를 유도한다.
3. 목록 준비도 같은 잠금을 사용한다. 이미 준비된 목록 읽기는 이 잠금을 기다리지 않는다.
4. 운영 DB에서 팀명 매칭용 네 필드만 조회한다. live/past를 모두 포함하고 파일 모드의 기존 동작을 유지한다.
5. 실패 시 마지막 정상 응답과 원래 생성 시각을 유지한다. 예측 선택·동결·원장·추천 수식은 변경하지 않는다.

## 격리된 샘플 측정

`py scripts/measure_response_memory.py`는 임시 DB만 사용한다.
120경기 × 선수 기록 1,000개를 넣고 Python tracemalloc으로 측정했다.

- 응답 캐시 잔류 Python 할당: 3,869,996 → 84,083 bytes (약 97.8% 감소).
- 응답 한 번 준비의 최대 Python 할당: 16,781,019 → 16,781,714 bytes. 단일 준비의 최대치는 줄지 않았다.
- 팀명 조회 잔류 Python 할당: 31,328,242 → 52,333 bytes.
- 팀명 조회 최대 Python 할당: 38,042,179 → 54,325 bytes.
- 팀명 조회 결과의 동일성도 확인했다.

합성 데이터 수치이며 운영 RAM 절감률이 아니다. SQLite 내부 파싱·네이티브 메모리는 tracemalloc에 포함되지 않는다. 반복 운영 RSS와 OOM 여부는 배포 후 따로 검증해야 한다.

## 검증 및 제한

- 동시 요청 20개에서 재조회 중복 방지, 실패 시 이전 데이터 유지, 미준비 응답, revision 갱신, 목록 준비와 산출물 처리 상호 배제를 회귀 테스트한다.
- Python 전체 테스트와 웹 테스트·빌드를 실행한다. 웹 테스트의 기존 Vite 포트/종료 경고와 npm audit high 1건은 이번 수정 범위 밖이다.
- 실시간 배당·점수 프로세스끼리의 중첩, MatchViews 전체 JSON 해석 순간의 최대 메모리, Python 할당자의 RSS 반환 문제는 이번 수정으로 해결했다고 주장하지 않는다.
- 큰 작업을 전부 직렬화하면 점수 최신성이 나빠질 수 있어 이 PR은 확인된 API 중복 처리부터 제한한다.
- 병합·배포·RAM 증설은 수행하지 않는다. 운영 검증 전에는 1GB 무중단 운영이 가능하다고 판정할 수 없다.

## 배포 후 검증 기준

동일 1GB에서 프로세스 RSS 추세, OOM/강제종료, API 응답과 generated_at/revision, 보조 작업 실제 완료를 비교한다. 경기 집중 시간과 6시간 전체 계산 주기를 포함해야 하며, 단일 빠른 응답이나 재시작 직후 여유 메모리를 성공 근거로 삼지 않는다.
