# 경기 목록·상세 조회 분리

## 변경

- `/api/matches?scope=recent`: KST 어제·오늘·내일만 조회. 어제 시작한 라이브 경기의
  기존 프런트 날짜 판정을 유지한다. 카드의 선택·확률·배당·동결 원장은 그대로 보낸다.
- 선수 자료는 카드에 표시할 이름만 먼저 보낸다. 경기 모달을 열면
  `/api/match-detail?key=...&revision=...`로 전체 선수 정보·기록을 가져온다.
- 상세는 목록 revision과 같을 때만 사용한다. 상세 응답으로 현재 배당·라이브 상태·
  동결 픽을 덮어쓰지 않는다. 버전 불일치는 409와 재조회 안내로 처리한다.
- `전체`를 누르면 `scope=all`로 과거·미래 경기까지 조회한다. 조회 중 기존 목록과
  선택한 필터를 유지하고 실패 시 재시도 버튼을 표시한다.
- 누적 성적을 펼칠 때만 기존 전체 `/api/picks`를 조회한다. 목록 축소본으로 전체
  적중률을 계산하지 않는다.
- 최근 추천 결과에 필요한 작은 정산 기록은 별도로 유지한다. 선수 자료를 제거해도
  과거 추천의 적중/실패 판정은 사라지지 않는다.
- 기존 전체 API는 유지한다. 백엔드가 아직 새 경로를 지원하지 않을 때(404)만
  기존 API로 돌아간다. 일시 503을 전체 대용량 재조회로 증폭시키지 않는다.
- DB 산출물은 수정하지 않는다. revision이 같으면 파싱 결과를 재사용하며,
  조회 캐시는 현재 날짜의 recent/all 두 종류로 제한한다.

## 크기 검증

2026-09-22 공개 picks 응답을 메모리에서 새 목록으로 변환한 결과:

- 전체 원본: 25,325,136바이트, 1,483경기.
- 초기 요약: 1,441,095바이트, 어제·오늘·내일 58경기와 작은 정산 기록 1,173개.
- 초기 요약 gzip(level 3): 173,432바이트.
- 비압축 크기 약 94.3% 감소. 전체 페이지 전송량이나 로딩 시간 감소율은 아니다.
  실시간 점수·배당·추천 API는 별도로 받으며 아직 운영 배포 전이다.

전체 보기와 누적 성적의 추가 다운로드는 남는다. 대용량 전체 API와 생성 주기의
서버 지연을 모두 해결했다고 주장하지 않는다. 첫 조회 시 원본 파싱은 여전히 필요하다.

## 검증

- Python 전체: 761 tests, 58 subtests 통과.
- 웹 전체: 232 tests 통과. 마지막 병렬 실행 중 Node의 IPC 역직렬화 오류가 한 번
  발생했고, 동일 코드의 단일 동시 실행 전체 테스트는 통과했다.
- Vite production build 통과.
- 회귀 테스트: 연말 KST 날짜, 경기 식별자, 원본 비변경, 과거 결과 보존,
  revision 불일치 차단, 캐시 재사용, 이전 API 호환, 동결 픽·가격 보존.
- 공개 운영 응답을 격리 SQLite DB에 복사해 로컬 서버·브라우저로 검증.
  오늘 10경기와 최근 추천 10건 중 6건 적중이 유지됐다.
  경기 상세의 선수 ERA·라인업 복원, 전체 필터 선택 유지 및 1,483경기 표시 확인.
  상세 API 정상 revision 200, 오래된 revision 409 확인.
- 누적 성적 추가 조회도 확인했다. 해당 원본은 기존 전체 계산 함수에서도
  정산 0/대기 1,199로 나오므로 UI는 기존과 같은 '집계 대기'다. 요약본으로
  전체 성적을 잘못 계산한 결과가 아니다.

## 배포

PR #221과 독립적인 후속 변경이다. 두 PR 모두 병합·배포는 별도 승인 대상이다.
권장 순서는 백엔드 새 경로 배포 후 프런트 배포다. 반대 순서도 404 fallback으로
동작하지만 백엔드 배포 전에는 데이터 절감 효과가 없다. Fly 인증이 없어 서버
로그·운영 배포 검증은 수행하지 않았다. 서버 재시작·운영 DB 변경도 없다.
