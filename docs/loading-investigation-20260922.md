# 로딩 지연 조사 (2026-09-22 KST)

## 확인한 내용

공개 운영 API를 GET으로 읽고 배포 화면을 확인했다. 단일 위치·소수 요청의
측정이므로 평균, p95 또는 모든 사용자의 로딩 시간으로 해석하지 않는다.

- 홈페이지 HTML: 200, 첫 응답/완료 약 0.26초, 1,562바이트.
- picks API 무압축: 첫 응답 3.06초, 완료 5.78초, 25,325,136바이트.
- picks API gzip: 첫 응답 5.34초, 완료 5.98초, 전송 2,355,997바이트.
- live-odds API 무압축: 첫 응답 0.16초, 완료 0.39초, 1,622,944바이트.
- today-recommendations API 무압축: 첫 응답 0.86초, 완료 1.10초, 533,735바이트.

gzip은 이미 작동한다. 압축 요청이 더 늦었던 단일 관측을 압축의 역효과라고
해석하면 안 된다. 네트워크와 서버 부하가 같지 않다. picks의 대용량 응답과
긴 첫 바이트 대기는 확인했으나 CPU·DB 잠금·네트워크별 기여도는 미확정이다.

배포 UI는 로딩 후 오늘 10경기(진행 중 3, 예정 7)를 표시했다. 사용자가 말한
정확한 '배당 측정중' 문자열은 현재 main 소스와 해당 화면에서 재현하지 못했다.
로딩 안내는 4초 뒤 '최신 배당과 저장된 사전 예측을 맞추고 있습니다', 12초 뒤
'경기 데이터가 많아 정리하는 중'으로 바뀌지만 실제 서버 작업 상태와 연결되지 않는다.
별도의 '배당 발표 전'은 배당대기 경기 상태이며 HTTP 로딩과 다르다.

09:23경 health 응답:
- 디스크 여유 1,485MB.
- odds_generated_at: 2026-09-22 08:45:14 KST.
- picks_generated_at: 2026-09-22 04:44:11 KST.
- picks_stored_at: 2026-09-22 08:55:41 KST.

저장 시각이 최근이어도 예측 생성 시각은 오래될 수 있다. 수집·예측 갱신 지연을
첫 화면 전송 지연과 구분해야 한다. publish는 주기 작업 전체가 끝난 후 30분을
더 기다리는 구조라 실행시간만큼 간격이 늘어난다. 이것만으로 이번 4시간 이상
생성 지연의 원인이라고 단정할 수 없다. Fly 로그 접근은 인증 부재로 실패했다.

## 구현한 개선

1. 서버 캐시 확인 전에 25MB JSON을 DB에서 읽던 순서를 수정했다. 작은 stored_at
   조회로 revision을 먼저 비교하고, 변경된 경우에만 JSON을 읽고 압축한다.
   응답 스키마·동결 픽·정산·추천 조건은 변경하지 않았다.
2. 경기 API 요청을 한 번에 하나만 실행한다. focus/online/타이머가 겹쳐도 중복
   요청하지 않는다. JSON 수신까지 15초 제한, 페이지 해제 시 취소한다.
   일시 실패는 마지막 정상값을 유지하고 정기/복귀 조회로 재시도한다.
3. 로딩 문구를 실제로 확인 가능한 '내려받는 중/서버 응답 지연'으로 바꿨다.

캐시 테스트는 동일 revision의 두 요청에서 본문 조회가 1회인 것과 revision
변경 후 재조회·삭제 후 503을 확인한다. 브라우저 요청 테스트는 중복 방지,
본문 대기 시간 초과, 재시도, 해제 후 콜백 방지를 검증한다.

## 후속 개선 우선순위

1. 오늘 경기 요약 API와 과거 기록/경기 상세 API 분리. 카드에 필요한 필드를 명시한
   계약 테스트 후 상세 모달을 열 때만 큰 근거 데이터를 조회한다. 기존 전체 API를
   임의로 잘라 사전 원장이나 과거 기록을 잃게 하면 안 된다.
2. 원장 revision 기반 ETag/조건부 조회. 지금은 매분 같은 picks까지 다시 받는다.
   최신성·모바일 복귀 계약을 지키며 변경 없는 응답을 304로 처리하도록 설계한다.
3. 서버 로그로 수집, 예측 생성, DB 저장의 소요시간과 마지막 성공/실패를 분리한다.
   갱신 단계별 지연을 확인한 뒤 가벼운 게시와 무거운 분석을 분리한다. 1GB 운영
   머신에서 생성기를 추가 병렬 실행하는 방식은 피한다.
4. 배당 미발표/수집 실패/예측 지연을 구분해 각 생성 시각과 함께 표시한다.

## 검증과 남은 한계

Python 760 tests와 58 subtests, 웹 232 tests, Vite 프로덕션 빌드 통과.
실제 운영 API와 배포 화면을 읽었으며 원본 DB와 서버 프로세스는 변경하지 않았다.
서버 수정 배포 전이므로 실제 이용자 로딩이 몇 초 줄었다고 주장하지 않는다.
Fly 인증 후 로그 확인과 배포 전후 동일 조건 반복 측정이 필요하다.
