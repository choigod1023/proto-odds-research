# 경기 목록 응답 사전 준비와 압축 캐시

## 확인한 문제

기존 MatchViews는 Python 중간 객체를 캐시하지만 HTTP 처리기는 매 요청마다
json.dumps와 gzip.compress를 다시 실행했다. /health는 생성시각만 필요하면서
artifact_metadata가 큰 payload_json의 length까지 계산했다. 운영에서는 CPU 대기
압박도 높았으므로, 응답 캐시만으로 모든 지연이 해결된다는 결론은 낼 수 없다.

## 변경

- 최근/전체 목록의 최종 gzip 바이트를 버전·KST 날짜별로 재사용한다.
- 메모리에는 압축 응답만 추가 저장한다. 비압축 클라이언트에는 이를 해제해 보낸다.
- 상세는 요청한 경기만 처리하고 별도 무제한 URL/키 캐시를 만들지 않는다.
- DB revision을 매 요청 확인한다. revision 변경이나 KST 날짜 변경 시 재구성한다.
  예전 응답을 새 revision인 것처럼 내보내거나 stale 허용 시간을 늘리지 않는다.
- 동일 캐시의 동시 요청/사전 준비는 하나의 재진입 잠금으로 중복 생성을 막는다.
- 서버가 열린 뒤 단일 백그라운드 스레드가 최근 목록을 30초마다 사전 준비한다.
  메모리 여유가 256MB 미만이거나 측정 불가면 사전 준비만 건너뛴다.
- 변경 없는 경우 사전 준비도 버전 확인 후 기존 바이트를 재사용한다.
- health는 payload 길이를 제외한 작은 메타데이터만 조회한다.
- 추천·동결·정산·브라우저 캐시 정책·DB 쓰기에는 변경이 없다.

## 테스트

Python 780 passed, 58 subtests passed. 웹 232개 테스트와 프로덕션 빌드 통과.
동시 요청 16개에서 gzip 생성 1회, 비압축 응답 동일성, revision 및 날짜 무효화,
상세 revision 거부, 메모리 압박시 사전 준비 생략, 사전 준비 실패시 스레드 생존을 검증했다.

scripts/benchmark_response_cache.py로 로컬 고정 자료에 대해 각 방식 100회 비교:

- 최근 목록 응답 준비 평균: 3.335ms → 0.0023ms.
- 전체 목록 응답 준비 평균: 57.359ms → 0.0031ms.
- 압축 응답 추가 보관량 합계: 579,868바이트(약 0.58MB).
- 압축 해제 후 응답 내용이 원래 목록과 동일함을 확인했다.

이 값은 캐시가 준비된 상태의 로컬 Python 처리 시간이다. DB 연결/실제 SQL I/O,
네트워크, 운영 CPU 경쟁, 최초 캐시 생성 비용은 포함하지 않는다. 현재 자료의 날짜
구성이 운영 DB와 다르므로 서버 응답이 위 수치로 빨라진다고 해석해서는 안 된다.

## 남은 검증

- 사전 준비가 끝나기 전 요청 또는 DB 변경 직후 요청은 여전히 재구성을 기다릴 수 있다.
- 새 revision 생성은 전체 picks 읽기와 상세 압축을 수행하므로 원래 비용이 남는다.
- 사전 준비 작업 자체도 같은 CPU를 사용한다. 배포 후 API p50/p95, CPU 압박,
  RSS와 데이터 최신성을 함께 측정해야 한다.
- 기존 #221의 다른 artifact 경로 전체 DB 읽기 개선은 이 PR에 포함하지 않았다.
- 이번 작업은 PR까지이며 운영 배포/유료 증설은 하지 않았다.
