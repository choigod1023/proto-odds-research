# 배당 수집 DB 조회 최적화 — 2026-09-26

## DB를 사용해도 메모리가 커지는 이유

운영 SQLite는 시계열/원장 테이블 외에 artifacts 테이블에 JSON 문서도 저장한다.
`get_artifact()`는 payload_json 전체를 가져와 `json.loads`로 Python 객체를 만든다.
따라서 DB 사용 자체가 필요한 행·필드만 읽는다는 뜻은 아니다.
배당 수집은 회차와 live 선택지의 게임번호/마켓/라인/배당만 필요한데도
기존에는 과거 경기·선수/분석 정보까지 포함한 picks_v2를 전체 디코딩했다.
시장 갱신 단계는 이후 해당 문서를 다시 읽는다.

운영 읽기 전용 SQL로 확인한 length(payload_json): picks_v2 24,347,630문자,
live_odds 1,897,018문자, live_scores 3,976,235문자.
SQLite TEXT length는 바이트 수가 아니다. DB 전체를 내려받거나 운영에서 벤치마크하지 않았다.

## 이번 변경

- 배당 수집용 필드를 SQLite에서 투영하고 Python에는 필요한 값만 전달한다.
- 메타데이터와 선택지를 한 read transaction으로 읽어 revision 혼합을 막는다.
- 배당 이력을 JSON 문자열로 왕복 복사하지 않고 deepcopy한다. 입력 변경 방지는 유지한다.
- 이전 배당 객체 참조를 픽 갱신 전에 해제한다. 빈 원천의 마지막 정상 배당 유지도 보존한다.
- DB 스키마·추천 정책·T-30·수집 주기·서버 사양은 바꾸지 않는다.

## 재현과 범위

`python scripts/benchmark_odds_context.py`

저장소 picks_v2 fixture를 임시 SQLite에 저장해 구/신 조회를 각각 별도 프로세스로 3회 실행한다.
운영 DB가 아닌 로컬 Windows/Python 3.14 측정이다.
조회 입력은 약 807만 문자(파일은 UTF-8 약 1,283만 바이트).
동일 consumer 입력을 SHA-256으로 비교하며 3쌍 모두 일치했다.

초기 측정: 구 조회 0.305~0.313초 / 신 조회 0.102~0.108초.
Python 추적 할당 peak: 39.97MiB / 2.06MiB.
프로세스 PeakWorkingSet: 96.76~96.83MiB / 44.57~44.78MiB.
tracemalloc은 SQLite native 할당을 포함하지 않으므로 프로세스 지표도 별도로 수집한다.
프로세스 peak에는 기동과 결과 검증 준비가 포함된다. 운영 Linux RSS와 동일한 지표는 아니다.
이 결과는 전체 서비스 메모리 절감률/운영 최대 메모리/무장애를 증명하지 않는다.

## 남는 문제와 다음 검증

SQLite JSON 함수도 원본 문서를 파싱한다. 이번 변경은 Python 객체와 전송량을 줄이지,
DB 안의 대형 문서 처리 자체를 없애지는 않는다.
live_market_refresh는 여전히 전체 picks를 읽고 저장한다. 향후 경기별 데이터 모델과
변경분 갱신은 revision/원장/마지막 정상값 동작을 검증하며 별도 변경해야 한다.
고빈도 작업의 시간·RSS, 6시간 전체 계산과 경기 집중 구간의 대기/최신성도 검증해야 한다.
JSON 투영으로도 CPU가 부족하면 지속 CPU 할당을 개선해야 한다. 코드 개선만으로
현재 shared CPU 제한과 반복 OOM이 해결됐다고 판단하지 않는다.
보조 작업 512MB gate는 실행 시작만 제어하므로 무기한 대기와 실행 후 메모리 증가가 남는다.
서버 후보(지속 CPU 1~2개, RAM 4GB)는 후속 전체 주기 측정으로 결정한다.
운영 병합·배포·증설은 이 변경 검증과 별도의 승인 단계다.
