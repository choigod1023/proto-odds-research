# KBO 전향 수집 독립 감사 계약과 차단 기준

기준 구현은 `eaa0172d75dcbc203cf29f0514886fd90d2db3aa`에 포함된 `experiments/kbo-m0-followup-20261103/forward.py`다. 이 문서는 구현 승인이나 source verification 증명이 아니라, 새 어댑터·runner·scheduler가 인계되면 실제 코드를 상대로 실행할 검토 기준이다. 공식 원천 수집은 이 감사 준비 단계에서 수행하지 않았다.

## P0: 상품과 정산 의미

- 원문에 표시된 공식 상품 종류, 회차·경기번호, 선택지별 ID와 라벨, 정상·판매중 상태, 두 가격, 해당 상품의 무승부·취소·연장·몰수 등 실제 정산 규칙을 동일한 버전의 공식 원문 또는 검증 가능한 공식 규정에 연결한다. 홈/원정과 선택지 방향을 고정하고 원문과 정규화를 왕복 검증한다. HTML/PDF/API를 다룬다면 응답 바이트, 상태·URL·수신시각·파서 버전·해시와 필요한 규정 버전을 보관한다.
- 공식 야구 3방향 상품이 확인되면 이를 홈/원정만 골라 2방향 무승부 환급으로 정규화해서는 안 된다. 3방향 무승부 선택지는 2방향 환급과 경제적으로 다르다. 선택지 이름만 같거나 가격 2개만 보인다는 이유로 규칙을 추정하지 않는다. 이 문서는 특정 실제 판매 상품의 성격을 미리 확정하지 않는다.
- 사전 고정 계약은 `full_game_2way` 및 `draw_void_refund`다. 원문과 공식 규정으로 **정확히 같은 상품임이 증명되지 않으면 적격 캡처와 `source_verified`는 차단**한다. 무승부 환급이 명시되지 않거나 독립 규정 확인이 안 되면 `unknown`으로 기록하고 연구 ROI 모집단에 넣지 않는다. 다른 상품을 평가하려면 별도 사전 등록과 사용자의 결정이 필요하다.
- 3방향 예: 가격 홈 1.8, 무 3.0, 원정 2.0, 결과 무승부인 경우 홈 베팅은 −1단위다. 계약의 2방향 무승부 환급에서는 같은 결과가 0단위다. 3방향 가격표를 2방향으로 바꿔 정산하면 이 차이가 사라진다. `test_market_semantics.py`는 이 계약 반례만 확인하며 실제 어댑터를 검증하지 않는다.

## 소스와 시점

- 신뢰 경계: 수집기가 신뢰된 공식 HTTPS 종단점에서 받은 **원문 바이트**와 완료 시각을 직접 기록하고, 원문 해시 검증 후 독립 파서로 정규화한 결과가 저장 값과 일치해야 한다. 사용자 제공 JSON, URL 문자열, 본문의 자체 해시, `source_verified=true` 주장만으로는 공식 원천이나 외부 인증 시각을 증명하지 못한다. 리다이렉트 최종 호스트·상태코드·응답 유형·캐시 연령도 검사한다. 날짜 없는 자료, 서비스 페이지 오류·캡차·빈 문서, API 오류 객체는 실패 처리한다.
- 공식 확정 발표의 홈/원정 선발, 순서가 있는 타자 9명, 고유 선수 ID와 홈/원정 팀, 공식 경기 ID, 경기일(KST), 시즌, 더블헤더 순번이 한 경기로 일치해야 한다. 예정·추정·경기 후 실제 출장 기록을 경기 전 확정 발표로 승격하지 않는다. announcement, odds, history와 확정 이벤트 각각의 최초 실수신 시각 및 lineage를 따로 보관한다.
- 선수 이력의 대상 경기 날짜는 대상 경기보다 이르며, 이력·정정 데이터의 최초 수신/관측 시각은 캡처 시각을 넘지 않아야 한다. 시각이 없으면 시간 적격이 입증되지 않은 것으로 둔다. 원문에서 값을 재생해 정규화 피처·스칼라·선수 소유자와 비교한다. 누락치를 사후 데이터로 채우지 않는다.
- 첫 **완전한 적격** 스냅샷은 원래 경기 시작 `T−30` 정각까지 허용한다. 각 원문 전체 수신, 검증, 예측 완료와 불변 기록 완료가 해당 기한 안에 끝나야 한다. 요청 시작 시각이나 서버에 주장된 과거 발표 시각을 최초 수신으로 쓰지 않는다. 미완전/부적격 입력과 그 이유도 기록해 이후 데이터로 과거 최초 수신을 꾸미지 않는다. 지연·우천 변경 시 원래 시작 시각과 모든 변경 원문을 보관하고 기존 경기의 cutoff를 사후에 연장하지 않는다.
- 원래 확정 모델·피처 정의·3방향 확률 1:1:1 평균 및 2방향 조건부 변환, 코딩·의존성·입력 해시를 고정한다. 가격·결과나 성적에 따라 재선택·재학습·소급 캡처하지 않는다. 독립 인증에 실패하면 staging으로만 남기고 전향 유효성 모집단에는 넣지 않는다.

## 결과·정정·장애와 실행

- 최초 적격 기회의 경기/상품 불변 키와 입력·예측·가격 원문을 기록하고 동일 기회 재호출·가격 변경은 덮어쓰지 않는다. 모델별 동일 표본을 확보한다. 결과는 경기 후 별도의 공식 원문으로 확인하며 결과 ID·날짜·팀·상태 및 점수와 상품 규칙을 대조한다. 무승부·취소·몰수 등은 해당 상품의 입증된 규칙으로 처리한다.
- 정정은 원본 기록을 바꾸지 않는 새로운 해시 연결 이벤트로 이전 버전, 새 원문, 수신시각, 사유와 새 정산을 남긴다. 최신 유효 정산을 유일하게 선택하고 이전 결산을 중복 집계하지 않는다. 정정 기록이 미구현이면 충돌을 거부하고 수동 검토 대상으로 격리한다. `forward.py`는 현재 정정 충돌을 거부하며 별도 정정 경로가 없다.
- runner 재시작, 중복 트리거, 병렬 실행, 프로세스 종료와 원장 부분 쓰기에서 동일 기회 한 번만 확정돼야 한다. 원자적 잠금·내구성·불완전 레코드 격리와 잠금 복구 절차를 검사한다. 다른 실행이 살아 있을 때 잠금을 임의 삭제하지 않는다. 종료 후 재시작이 누락을 과거 수신으로 채워서는 안 된다.
- scheduler는 명시적으로 설치·활성화된 경우에만 실행된다. 중복 등록·중복 실행 방지, KST/UTC·서머타임과 시스템 시계 오류, 로그 및 실패 알림 경로, 종료와 복구를 점검한다. 절전·최대절전·종료 중에는 수집되지 않을 수 있으며 깨어난 후 T−30을 지난 기회는 결측이다. PC가 꺼져도 수집된다고 약속하지 않는다. 자동 깨우기는 실제 설정과 권한을 검증하기 전까지 가정하지 않는다.
- 외부 요청은 사용자가 승인한 제한과 서비스 정책을 준수하고 시간초과·캐시·backoff·중지 조건을 둔다. 영구 반복, 조기 유리한 시점만 선택, 운영 추천·월 5만원 원장 변경, 자동 모델 채택을 하지 않는다. 정식 첫 검토 최소 기준 200개 신규 정산 쌍과 8주는 허용 조건일 뿐 효과 입증이 아니다.

## 인계 시 절차

1. runner·어댑터·scheduler와 테스트의 고정 commit 및 파일 해시, 실행 경로, 원문 샘플과 규정 버전을 확보한다. 원문은 민감정보를 제거하되 실질 증거와 의미가 유지돼야 한다.
2. `regression-cases.json`의 각 기대 결과를 실제 구현의 독립 테스트로 실행한다. 사례 명세 자체의 통과는 구현 통과가 아니다.
3. 실제 고정 소스에 대해 원문→정규화·모델 입력·불변 원장→결과 정산까지 대조하고 실패 사례를 재현한다. 테스트 전후 원장·scheduler·운영 서비스에 영향이 없는 임시 경로를 쓴다.
4. 실행된 테스트, 차단된 사례, 미확인 공식 규칙·source authentication·시각 신뢰 한계, 실제 적용·운영 여부를 분리해 보고한다.
