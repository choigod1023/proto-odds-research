# MLB timecode 과거 경계 확인 — 2026-11-03

공식 MLB `feed/live/timestamps`와 `feed/live?timecode=...`를 실제로 비교했다. [앞선 공식 원천 수집 PR #527](https://github.com/choigod1023/proto-odds-research/pull/527)의 2026년 4·6·9월 각 1경기를 대상으로, 경기 2일 전 시각을 요청한 응답과 이미 보존한 T-35 응답을 바이트 단위로 비교했다. 신규 공식 요청은 7회이며 모두 HTTP 200, 요청 사이 수신 완료 후 최소 1초를 지켰다. 원문과 요청 URL·현재 수신 시각·상태·SHA256을 `evidence/`에 보존했다.

세 경기 모두 요청한 2일 전 시각보다 **나중**인 타임스탬프가 반환됐고, 그 시각은 해당 경기의 공식 timestamps 목록 첫 항목과 같았다. 2일 전 요청 응답은 T-35 요청 응답과 3/3개 모두 SHA256이 같으며 양 팀 9명 타순을 포함했다.

- gamePk 824940: 요청 `20260330_161500`, 반환·목록 첫 항목 `20260401_133009`, 다음 항목 `20260401_155029`, 목록 440개.
- gamePk 822974: 요청 `20260530_224000`, 반환·목록 첫 항목 `20260601_191035`, 다음 항목 `20260601_222020`, 목록 577개.
- gamePk 822855: 요청 `20260830_000500`, 반환·목록 첫 항목 `20260831_202343`, 다음 항목 `20260831_234008`, 목록 436개.

모든 시각은 UTC다. 세 사례의 첫 항목은 T-35 이전이고 두 번째 항목은 T-35 이후다. 이 사례에서는 목록상 첫 기록보다 이른 시각을 요청해도 서버가 오류 대신 첫 기록을 돌려준다. **요청 timecode만 보고 그 이전에 선수가 발표됐다고 판단하면 미래 정보가 들어간다.** 해당 2일 전 응답 3개는 요청 시점 기준 부적격이다. 세 경기 이외에 같은 동작이 항상 발생한다고 단정하지 않는다.

공급자 timestamp가 T-35보다 이르다는 사실과 play 이벤트의 과거 재생은 별개 선수 필드의 최초 발표·실제 수신을 증명하지 않는다. 세 경기의 첫 기록에 양 팀 9명이 있었다는 관찰도 당시 명단 발표를 인증하지 않는다. 과거 HTTP 수신은 지금 이뤄졌으며, 원문 해시는 보관 바이트의 무결성을 확인할 뿐 독립적인 과거 수신 증거가 아니다. 기존 102경기 전체에 새 검사를 확장하지 않았고 strict PIT 인증은 계속 0이다. 모델 학습, ROI, 운영 동결 기록 변경은 없다.

검증: `python -X utf8 experiments/mlb-asof-verification-20261103/verify.py`, `python -X utf8 -m pytest tests/test_mlb_asof_verification_20261103.py -q -p no:cacheprovider`. 스크립트는 7개 신규 원문 및 이전 T-35 원문 해시, 목록 순서, 요청 시각과 반환 시각, 요청 간 간격, 바이트 일치와 선수 수를 재검사한다. 요청 시각 이후의 제공자 시각을 거부하는 단위 검사도 포함한다.

다음에는 각 경기의 실제 사전 수신 또는 선수별 공식 변경·발표 시각을 독립적으로 확인해야 한다. 현재 목록만으로는 선수 필드의 시점 신뢰성을 보장하지 않으므로 이 응답을 확정 선발·타순의 전향 자료로 승격하지 않는다.
