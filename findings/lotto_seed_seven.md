# 128비트 로또 시드 7회 적중 탐색

학습 1~740회에서 1등을 7번 이상 맞힌 시드는 이번 범위에서 찾지 못했습니다. 따라서 해당 시드가 이후 회차에서 무작위보다 나은지는 검증할 대상이 없습니다. 이는 무작위와 성능이 같다고 검증했다는 뜻이 아닙니다.

## 실제 탐색 결과

- 홀수 부분 시드: 4,000,000,000개. 2회 이상 180,574개, 3회 이상 4개, 4회 이상 0개.
- 짝수 부분 시드: 4,000,000,000개. 2회 이상 181,515개, 3회 이상 3개, 4회 이상 0개.
- 누적 부분 시드 80억 개 중 이번에 새로 계산한 부분 시드는 40억 개입니다. 이전 실험의 40억 개는 검증 후 재사용했습니다.
- 각 부분의 최대 적중 횟수를 더하면 6회입니다. 이 범위의 어떤 홀수·짝수 조합에서도 7회 이상은 나올 수 없습니다.
- 7회 이상 완성 시드: 0개. 이후 회차 비교: 미실시(검증 대상 없음).
- 추가 탐색과 기록 처리에 걸린 시간: 491.75초. 이전 범위의 계산 시간은 포함하지 않습니다.

80억 개는 128비트 완성 시드 80억 개를 독립적으로 검사했다는 뜻이 아닙니다. 홀수와 짝수의 64비트 부분을 각각 40억 개 검사하고, 두 부분의 적중 횟수가 더해지는 구조를 이용했습니다. 완성 시드끼리는 부분 수열을 공유합니다.

## 방법과 검증

기존 `splitmix64-paired128-v1` 생성기를 유지했습니다. 상위 64비트는 홀수 회차, 하위 64비트는 짝수 회차를 생성하며, 시드 하나는 회차마다 한 게임을 생성합니다. 첫 홀수·짝수 회차인 1회와 2회는 역산으로 반드시 맞히게 만든 후보입니다. 이 두 적중을 예측 능력으로 해석할 수 없습니다.

고정된 학습 구간은 1~740회입니다. 기존 아핀 순열의 인덱스 [0, 20억)을 보존하고 [20억, 40억)을 추가했습니다. offset=20261015, stride=1000003을 그대로 사용했습니다. 두 프로세스가 각각 네 개의 C++ 스레드로 계산했으며, 1억 개 단위로 결과를 저장했습니다. 새 탐색 전 후보 수와 선별 기준을 protocol.json에 고정했습니다.

7회 선별 기준은 각 부분 최소 3회, 합계 최소 7회이며 4+3과 3+4를 모두 포함합니다. 이번에는 양쪽 전체 히스토그램의 최대가 3회라서, 최소 3회 필터 밖의 후보를 포함하더라도 7회가 불가능합니다.

기존 체크포인트는 생성기 소스·학습 데이터·추첨 원장 해시를 확인한 뒤 재사용했습니다. 독립적인 스칼라 Python 검증으로 모든 3회 이상 생존 후보의 실제 적중 회차, 아핀 순열에서의 위치, 배치 범위의 연속성, 파일 해시 및 최종 집계를 재검산했습니다. 80억 개 비생존 후보를 Python으로 전부 다시 돌린 것은 아닙니다. 축소된 합성 실험에서는 단일/병렬 실행과 이어 계산/전체 직접 계산이 같음을 확인했고, 전체 관련 테스트 22개가 통과했습니다.

검증용 구간 741~990회와 최종 구간 991~1238회는 이전 실험에서 이미 확인한 구간입니다. 후보를 찾았더라도 새 전향적 검증으로 부를 수 없습니다. 이번에는 후보가 없어 두 구간의 성능 통계를 만들지 않았습니다. 원장은 기존 1~1238회 자료를 사용했고 최신 회차를 추가 수집하지 않았습니다.

## 왜 후보를 늘려도 찾기 어려운가

로또 6/45 조합은 8,145,060개입니다. 각 부분은 학습 370회 중 첫 회차를 이미 맞히므로, 부분 4회 적중에는 나머지 369회에서 세 번을 더 맞혀야 합니다. 독립·균등 근사에서 그 확률의 주항은 C(369,3) / 8,145,060^3 ≈ 1.5371×10^-14입니다. 누적 80억 개에서 기대되는 4회 적중 부분 시드는 약 0.000123개입니다.

이 계산은 결정론적 생성기의 독립성을 증명하지 않는 근사이며, 실제 탐색 결과를 대신하지 않습니다. 병렬화는 탐색 속도를 높이지만 적중 확률을 높이지 않습니다. 이번 실패가 전체 128비트 공간에서 7회 적중 시드가 존재하지 않는다는 증명도 아닙니다.
