# 로또 시드 실험 병렬화와 양자컴퓨팅 검토

128비트 실험의 홀수·짝수 후보 탐색, 검증·최종 평가를 각각 독립 프로세스 두 개로 나눠 실행하도록 변경했습니다. 번호 생성·생존 조건·구간·무작위 대조군의 공유 구조는 그대로 유지합니다. 계산 시간을 줄이는 기능이며 미래 당첨 확률을 높이는 기능은 아닙니다.

## CPU 병렬 실행

```powershell
python src/lotto_seed_128.py --workers 2 --output .local-build/parallel-run
python src/lotto_seed_128.py --workers 1 --output .local-build/serial-run
python scripts/benchmark_lotto_parallel.py
python -m pytest tests/test_lotto_seed_128.py tests/test_lotto_seed_expanded.py tests/test_lotto645.py -q
```

`--workers 1`은 순차 실행, `--workers 2`는 두 프로세스 실행입니다. Windows에서도 동작하도록 spawn 방식으로 자식 프로세스를 시작합니다. 프로세스 시작·입출력·메모리 복사 비용이 있으므로 코어 수만큼 선형으로 빨라지는 것은 아닙니다. 동시에 여러 작업을 실행하는 환경을 고려해 이 기능에서는 최대 두 프로세스로 제한했습니다.

대조군 난수는 부모 프로세스에서 동일하게 생성해 각 평가 작업에 전달합니다. 결과는 실행 완료 순서가 아니라 홀수·짝수 및 검증·최종 구간의 지정된 이름으로 수집합니다. 병렬 실행이 시드나 평가 결과를 바꾸지 않는지 테스트합니다.

벤치마크는 부분별 후보 100만 개, 대조군 1만 회라는 동일 작업을 `1→2→2→1` 프로세스 순서로 실행합니다. 전체 CLI 벽시계 시간에는 프로세스 시작과 보고서 저장도 포함됩니다. 선별 및 평가 단계 시간도 별도로 저장합니다. 네 실행의 생존 목록과 전체 평가 JSON을 정규화해 SHA-256 해시가 같은지 확인합니다. 실행 파일은 같은 소스이고 생성기 버전도 같습니다.

실측 수치는 함께 저장한 `data/lotto/reports/parallel-benchmark.json`을 참고하세요. 로컬 환경의 각 방식 두 번 측정이며 통계적 성능 보증은 아닙니다. CPU 수, 메모리 대역폭, 동시에 실행 중인 작업에 따라 결과가 달라질 수 있습니다.

실제 측정에서 순차 실행은 39.817초와 40.374초, 두 프로세스 실행은 25.195초와 22.647초였습니다. 중앙값은 각각 40.096초와 23.921초로, 약 1.676배 빠르고 전체 시간을 약 40.34% 줄였습니다. 이 작업에서는 병렬화가 유효해 CLI 기본값을 `--workers 2`로 설정했습니다. 작은 작업이나 메모리가 제한된 환경에서는 `--workers 1`로 전환할 수 있습니다.

네 실행 모두 생존 시드 3,008개와 검증·최종 평가의 전체 결과 해시가 같았습니다. 19개 테스트를 통과했고, 병렬 실행 결과의 3,723,904티켓을 별도 스칼라 Python 계산으로 교차 검증했습니다. 검증 요약은 `data/lotto/reports/parallel-verification.json`에 보존했습니다.

## 양자컴퓨팅을 바로 붙이지 않은 이유

Grover 알고리즘은 비구조적 탐색에서 이론적으로 이차 속도 향상을 제공합니다. 하지만 후보가 조건을 만족하는지 판정하는 오라클이 필요합니다. [IBM Quantum Learning](https://quantum.cloud.ibm.com/learning/en/courses/fundamentals-of-quantum-algorithms/grover-algorithm/introduction), [IBM Grover 튜토리얼](https://quantum.cloud.ibm.com/docs/en/tutorials/grovers-algorithm).

이 저장소의 경우 오라클은 시드에서 번호를 만들고, 학습 회차의 당첨 번호와 비교하고, 적중 횟수를 세어 기준을 충족하는지 판정해야 합니다. 이 판단은 현재 코드에 근거한 구현 요구사항입니다. 기존 Python 또는 C++ 함수를 양자 장비에 그대로 보내는 것으로 끝나지 않으며, 곱셈·나머지·비교·계수 등의 가역 회로와 보조 큐비트가 필요합니다. 이 전체 회로의 게이트 수나 실행 시간을 아직 측정하지 않았으므로 양자 방식이 더 빠르다고 주장할 수 없습니다.

IBM 공식 튜토리얼도 Grover의 회로 깊이와 현재 장비의 잡음 때문에 작은 규모의 하드웨어 예제를 사용한다고 설명합니다. 그 제약을 고려하면, 이 프로젝트에서 당장 실용적인 가속을 확인할 방법은 CPU 병렬 실행과 기존 벡터화의 측정이라는 판단입니다. [IBM 하드웨어 예제 및 제약](https://quantum.cloud.ibm.com/docs/en/tutorials/grovers-algorithm).

이미 정답 시드를 고전적으로 찾아 둔 뒤 그 목록을 표시하는 작은 Grover 예제는 원리 시연에는 도움이 되지만, 원래 탐색을 양자로 가속했다는 증거가 되지 않습니다. 또한 여기서는 홀수·짝수 부분 분해와 조건부 역산으로 고전 계산량을 줄였습니다. 향후 양자 우위를 평가한다면 단순 128비트 완전탐색뿐 아니라 이러한 고전 최적화와도 비교해야 합니다.

일반적인 밀집 상태벡터 방식으로 128큐비트를 시뮬레이션할 때는 complex128 기준 `16 × 2^128`, 약 `5.44 × 10^39`바이트가 필요합니다. 이는 Python 정수 계산으로 확인한 저장 공간 산식이며, 특수한 구조를 이용하는 모든 시뮬레이터가 같은 메모리를 필요로 한다는 뜻은 아닙니다. 일반 노트북의 시뮬레이터를 추가했다고 대규모 양자 계산의 속도 이점이 생기지는 않습니다.

현재 변경에는 실제 양자 장비 실행, 유료 작업 제출, 양자 SDK를 이용한 성능 주장이 없습니다. 양자 회로의 조건 판정에 미래 당첨 번호를 넣을 수는 없으므로, 과거에 맞는 시드를 더 빨리 찾는 것과 미래를 더 잘 맞히는 것은 별도의 문제입니다.
